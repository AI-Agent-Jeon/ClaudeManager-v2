> 버전: v1.0 (2026-09-01)
> 적용 대상: SDLC 7개 스킬 전부 (plan, analyze, design, develop, test, deploy, operate)
> **이 계약은 각 SKILL.md의 절차보다 우선한다.** 스킬 절차와 충돌하면 이 문서를 따른다.

## 왜 이 문서가 있는가

2026-09-01 Phase 1 설계 단계에서 아래 사고가 발생했다. 전부 **"사람이 읽으면 아는데 에이전트는 모르는 것"** 때문이었다.

| 사고 | 원인 | 대응 조항 |
|------|------|----------|
| ANL-001~004가 Notion에만 존재 → "analyze 건너뜀" 오진단 → 존재하지 않는 안건(D-15) 상정 | 스킬에 Notion↔Git 이중 기록 절차 없음 | §3 |
| `ls`로 사전 점검 통과 → 빈 껍데기 문서도 통과 | 존재 검증만 있고 내용 검증 없음 | §1 |
| design 산출물이 계획(DES-001~009) 대비 015까지 67% 초과 | 계획 대비 편차 감지 없음 | §1 L3 |

## §0. 재개 확인 — 스킬 시작 시 최초 동작

에이전트 세션은 끊긴다. 컨텍스트는 요약된다. **재개 지점이 파일에 없으면 에이전트는 처음부터 다시 하거나, 더 나쁘게는 하지 않은 단계를 했다고 가정한다.**

### 상태 파일

경로: `.orchestrator/status/{skill}.json`

```json
{
  "skill": "design",
  "phase": 1,
  "started_at": "2026-09-01T10:00:00+09:00",
  "updated_at": "2026-09-01T14:30:00+09:00",
  "current_step": 7,
  "completed_steps": [1, 2, 3, 4, 5, 6],
  "artifacts": [
    { "code": "DES-001", "git": "docs/design/des-001-architecture.md", "notion": "https://app.notion.com/p/..." }
  ],
  "blocked_on": null
}
```

### 규칙

1. 스킬 시작 시 **가장 먼저** 이 파일을 읽는다. 없으면 생성하고 `current_step: 1`로 시작한다.
2. 있으면 `completed_steps`의 **다음 단계부터** 재개한다.
3. 각 단계를 끝낼 때마다 **즉시** 갱신한다. 여러 단계를 몰아서 기록하지 않는다.
4. 대표 결정 대기로 멈출 때는 `blocked_on`에 결정 ID(예: `"D-30"`)를 적는다.

### 금지

- ❌ `completed_steps`에 없는 단계를 수행했다고 가정하는 것
- ❌ 상태 파일을 읽지 않고 절차 1단계부터 재실행하는 것 (이미 만든 산출물을 덮어쓴다)
- ❌ 스킬 종료 시 상태 파일을 지우는 것 (다음 Phase의 감사 근거다)

## §1. 사전 점검 — 3단 검증

`ls`는 **빈 파일도 통과시킨다.** 그리고 에이전트에게 체크리스트는 *통과시켜야 할 관문*이라, 형식만 맞추고 넘어가는 방향으로 압력이 걸린다. 검증을 3단으로 나눈다.

### L1 — 존재

파일이 있는가. `ls` 또는 `test -f`.

### L2 — 내용

**파일이 있다는 것과 쓸모 있다는 것은 다르다.** 아래를 전부 확인한다.

```bash
# (1) 빈 파일 차단
for f in <대상 파일들>; do [ -s "$f" ] || echo "EMPTY: $f"; done

# (2) 요구사항/산출물 코드가 실제로 채번되어 있는가
grep -cE '\b(FR|NFR|UIR|DAT|INT|PLN|ANL|DES|DEV|TST|DPL|OPS)-[0-9]{3}\b' <파일>

# (3) Notion 원본 링크가 헤더에 있는가 (§3 위반 탐지)
grep -L 'Notion' <대상 파일들>
```

`(3)`의 출력에 파일이 하나라도 나오면 **§3 이중 기록이 깨진 상태**다. 그 파일은 Git에만 있거나 Notion에만 있을 가능성이 높다.

### L3 — 정합

계획된 산출물 개수와 실제 개수를 대조한다.

```bash
find docs/design -name 'des-*.md' | wc -l   # 실제
grep -oE 'DES-0[0-9]{2}' docs/plans/pln-002-phase1-plan.md | sort -u | wc -l  # 계획
```

### 판정

| 결과 | 조치 |
|------|------|
| L1 실패 | 이전 스킬 회귀 제안. **진행 차단** |
| L2 실패 | 해당 문서에 대해 이전 스킬 회귀 제안. **진행 차단** |
| L3 편차 | 대표에게 보고. **차단하지 않음** — 범위가 늘어난 정당한 사유가 있을 수 있다. 단 §5 트리거를 확인한다 |

### 금지

- ❌ `ls`가 성공했다는 이유만으로 통과 처리
- ❌ L2·L3를 "파일이 있으니 괜찮다"고 건너뛰는 것
- ❌ 점검 실패를 보고하지 않고 우회하는 것

## §2. 결정 전파 (Decision Propagation)

결정 하나가 문서 하나만 바꾸는 일은 거의 없다. **D-16 하나가 승인되면 PLN-001·PLN-002·PLN-003·DES-014 네 문서를 고쳐야 한다.** 에이전트는 지시받은 문서 하나만 고치고 끝내므로, 전파를 절차로 강제한다.

### 절차

1. **영향 문서 목록을 먼저 산출한다.** 고치기 전에 만든다.
   ```bash
   grep -rln "D-16\|FR-018\|승인 게이트" docs/
   ```
2. `docs/00-approvals.md`의 해당 결정 행에 **영향 문서**와 **반영 상태**를 기록한다.
3. 전건 반영한다.
4. **잔여 확인** — 결정으로 바뀐 옛 표기가 남아 있지 않은지 전수 검색한다.
   ```bash
   # 예: 의사결정 승인 UI가 Phase 3 → Phase 1로 바뀐 경우
   grep -rn "의사결정 승인 UI" docs/ | grep -i "phase 3"
   ```
   출력이 비어야 통과다.

### 금지

- ❌ **"변경 예정" · "반영 대기" · "개정 대상" 상태로 스킬을 종료하는 것.** 이 상태는 다음 세션에서 잊힌다. 실제로 PLN-003이 이 상태로 방치됐다
- ❌ 영향 문서 목록을 만들지 않고 눈에 띄는 문서만 고치는 것
- ❌ 잔여 확인 없이 반영 완료를 보고하는 것

## §3. 이중 기록 (Notion ↔ Git)

`CLAUDE.md`는 **Notion = 대표 승인 원본, Git = 에이전트 실행 원본**이라고 선언한다. 그런데 이 규칙이 스킬 절차에 없으면 에이전트는 한쪽에만 쓴다. ANL-001~004 사고의 직접 원인이다.

### 규칙

**모든 산출물은 Git과 Notion 양쪽에 존재해야 한다.** 한쪽만 만들고 완료 보고하는 것은 미완료다.

| 대상 | 위치 |
|------|------|
| Git | `docs/` 하위 규정 경로 (CLAUDE.md §디렉토리 구조) |
| Notion | `02. 프로젝트 / ClaudeManager / {NN. 단계}` 하위 |

### 문서 헤더 필수 형식

모든 산출물 문서는 헤더에 아래를 포함한다. **이것이 이중 기록의 기계 판독 가능한 증거다.**

```markdown
> **원본**: [Notion {코드}](https://app.notion.com/p/...) · Git 동기화 {YYYY-MM-DD}
> 기준 원본 정책: Notion = 대표 승인 원본 / Git = 에이전트 실행 원본. 충돌 시 Notion 우선.
```

### 추가 의무

- `docs/00-progress.md`의 **산출물 동기화 현황** 표에 행을 추가한다
- Notion `00. 진행 상황` 페이지도 함께 갱신한다 (Git `docs/00-progress.md`의 미러)

### 검증

```bash
find docs -name '*.md' ! -name 'CLAUDE.md' -exec grep -L 'Notion' {} +   # 출력이 비어야 통과
```

### 금지

- ❌ Git에만 쓰고 완료 보고 (Notion 승인 원본이 없어 대표가 검토할 수 없다)
- ❌ Notion에만 쓰고 완료 보고 (다음 스킬의 사전 점검이 "누락"으로 오판한다 — ANL 사고의 재현)
- ❌ Notion URL 없이 헤더를 작성하는 것

## §4. 보고 전 산출물 검증

보고 형식에 `## 산출물` 칸이 있지만, **거기 적힌 파일이 실제로 존재하는지 확인하는 절차가 없으면 에이전트는 만들지 않은 파일을 적는다.** 상위 에이전트는 그 보고를 그대로 대표에게 전달한다.

### 절차

보고서를 대표/상위 에이전트에게 보내기 **직전에** 실행한다.

```bash
# 산출물 칸에 적은 모든 경로
for f in <보고서의 산출물 경로 전건>; do
  [ -f "$f" ] && echo "OK   $f" || echo "MISSING $f"
done
```

1. `MISSING`이 하나라도 있으면 **보고를 중단한다**
2. 누락을 채운 뒤 재검증한다
3. 채울 수 없으면 산출물 칸에서 지우고, `## 미해결 사항`에 사유와 함께 옮긴다

### 금지

- ❌ 만들지 않은 파일을 산출물로 기재하는 것
- ❌ "생성 예정"인 파일을 산출물로 기재하는 것
- ❌ 검증을 건너뛰고 보고하는 것

## §5. 범위 변경 트리거

Phase 1의 Must가 12 → 19개, 복잡도 L이 2 → 6개로 늘어난 것을 **사람이 PLN-002 v2를 쓰면서 발견했다.** 자동으로 걸려야 한다.

### 트리거 조건

아래 중 **하나라도** 해당하면 Phase 재산정이 필요하다.

| 지표 | 임계 |
|------|------|
| Must 스토리 개수 증감 | **≥ 20%** |
| 복잡도 L 항목 개수 | **≥ 2배** |
| DB 테이블 개수 증감 | ≥ 50% |
| 구현 Layer 개수 | +1 이상 |

### 조치

1. 트리거 발동을 **즉시 대표에게 보고**한다 (의사결정 등급 **높음**)
2. plan 스킬 회귀 → PLN-002 Phase 계획서를 재산정한다
3. 재산정 결과 한 Phase가 과대해지면 **Phase 분할을 선택지로 제시**한다 (Walking Skeleton의 이점인 "빠른 동작 확인"이 사라지기 때문)

### 검사 시점

- plan 스킬: 8단계 다중 관점 자체 검토 시
- analyze / design 스킬: 승인 반영으로 요구사항이 추가된 직후
- 승인 처리 직후 (§2 결정 전파와 함께)
