## 디스패치

### 사전 점검

1. DPL-001~004 존재 여부: `ls docs/deploy/ docs/releases/ 2>/dev/null`
2. 현재 브랜치 확인: `git branch --show-current`

누락 산출물이 있으면 deploy 스킬 회귀를 제안한다.

### 위임

사전 점검 통과 시, project-agent를 생성한다:
- subagent_type: `project-agent`
- 전달: 스킬 `operate`, 경로 `.claude/skills/operate/SKILL.md`

### 완료 후

project-agent 완료 시:
1. 결과를 대표에게 전달
2. 다음 스킬 전환 정보에 따라:
   - 자동 → 해당 스킬 즉시 실행
   - 승인 필수 → 대표에게 실행 여부 확인

## 절차

### 1단계: 인시던트 분류 — P0~P3

보고된 이슈를 심각도로 분류한다.

| 등급 | 기준 | 대응 시간 | 행동 |
|------|------|----------|------|
| **P0 (치명)** | 시스템 전체 불능, 데이터 손실 위험 | 즉시 | 롤백 우선 검토, 대표 즉시 보고 |
| **P1 (높음)** | 핵심 기능 불능, 우회 불가 | 4시간 내 | 원인 분석 착수, 대표 보고 |
| **P2 (보통)** | 부분 기능 장애, 우회 가능 | 1일 내 | 정상 프로세스로 처리 |
| **P3 (낮음)** | 사소한 문제, UX 개선 | 다음 Phase | OPS-005에 기록, 즉시 수정 안 함 |

**P0 즉시 조치**: 롤백 계획(DPL-004)을 확인하고, 롤백이 가능하면 대표 승인 후 롤백한다. 롤백 후에도 근본 원인 분석은 계속한다.

**P3 처리**: 버그 리포트에 기록만 하고 다음 Phase 피드백(OPS-005)에 포함한다. 2단계 이후는 건너뛴다.

### 2단계: 증상 파악 + 재현

- 에러 메시지, 스택 트레이스, 로그 수집
- 재현 조건 식별 (입력, 환경, 순서)
- 동일 환경에서 재현 시도
- 재현 성공 시 → 3단계 진행
- 재현 불가 시 → 대표에게 보고하고 판단 요청 (AskUserQuestion)

**재현 기록 형식**:
```
- 환경: {OS, 브라우저, 버전}
- 재현 단계: 1. ... 2. ... 3. ...
- 예상 결과: ...
- 실제 결과: ...
- 재현율: {항상 / 간헐적 / 미재현}
```

### 3단계: 근본 원인 분석 — 5 Whys

표면 증상에서 시작하여 "왜?"를 반복하며 근본 원인을 추적한다. 최소 3회, 최대 5회 반복한다.

```markdown
### 5 Whys 분석

**증상**: {관찰된 문제}

1. **왜?** → {직접 원인}
2. **왜?** → {그 원인의 원인}
3. **왜?** → {더 깊은 원인}
4. **왜?** → {구조적 원인} (해당 시)
5. **왜?** → {근본 원인} (해당 시)

**근본 원인**: {최종 식별된 원인}
**원인 유형**: 코드 결함 | 설계 결함 | 요구사항 누락 | 환경 문제 | 외부 의존성
```

**원인 유형별 후속 조치**:

| 원인 유형 | 행동 |
|----------|------|
| 코드 결함 | dev-sub에게 수정 위임 (5단계) |
| 설계 결함 | design 스킬 회귀 제안 + 대표 보고 |
| 요구사항 누락 | OPS-005에 기록, 다음 Phase plan에 반영 |
| 환경 문제 | 환경 설정 수정 (DPL-002 갱신) |
| 외부 의존성 | 우회 방안 마련, 대표 보고 |

### 4단계: 가설 수립 + 검증

근본 원인에 대한 가설을 세우고, 코드/로그로 검증한다.

```markdown
### 가설 검증

| 가설 | 검증 방법 | 결과 |
|------|----------|------|
| {가설 1} | {코드/로그/테스트} | ✅ 확인 / ❌ 기각 |
| {가설 2} | ... | ... |
```

확인된 가설을 기반으로 수정 방향을 결정한다.

### 5단계: dev-sub 수정 위임

확인된 근본 원인과 수정 방향을 dev-sub에게 전달한다.

**전달 사항**:
- 근본 원인 (5 Whys 결과)
- 수정 범위 (최소 범위 원칙)
- 재현 테스트 작성 요청 (버그 재현 → 수정 후 통과)
- 관련 파일 경로

### 6단계: test-sub 회귀 테스트 위임

dev-sub 수정 완료 후 test-sub에게 회귀 테스트를 위임한다 (dev-sub과 병렬 불가 — 수정 완료 후 실행).

**전달 사항**:
- 수정된 파일 목록
- 기존 테스트 스위트 실행
- 재현 테스트 실행
- 영향 범위 내 관련 테스트 확인

### 7단계: Post-mortem 작성 (P0/P1만)

P0 또는 P1 인시던트인 경우, Post-mortem을 작성한다. P2 이하는 버그 리포트만 작성한다.

```markdown
### Post-mortem: {인시던트 제목}

**일시**: {YYYY-MM-DD HH:MM}
**심각도**: P0 / P1
**영향 범위**: {영향받은 기능/사용자}
**해결 시간**: {감지 ~ 해결 소요 시간}

#### 타임라인

| 시각 | 이벤트 |
|------|--------|
| HH:MM | 이슈 감지 |
| HH:MM | 원인 파악 |
| HH:MM | 수정 배포 |
| HH:MM | 정상 확인 |

#### 근본 원인
(5 Whys 결과 요약)

#### 재발 방지 조치

| 조치 | 유형 | 담당 | 기한 |
|------|------|------|------|
| {조치 1} | 예방 / 감지 / 완화 | agent / 대표 | {날짜} |

#### 교훈
(이번 인시던트에서 배운 점 — `.orchestrator/learnings.jsonl`에도 기록)
```

### 8단계: Phase 피드백 수집 — KPT 회고

이번 Phase 전체를 돌아보며 피드백을 구조화한다. 대표에게 각 항목을 확인한다 (AskUserQuestion).

```markdown
### KPT 회고

#### Keep (잘된 점 — 계속할 것)
- {구체적 사례와 이유}

#### Problem (개선할 점 — 문제였던 것)
- {구체적 사례와 영향}

#### Try (시도할 점 — 다음에 해볼 것)
- {구체적 행동과 기대 효과}
```

**수집 방법**:
1. 운영 중 발견된 이슈 목록 정리
2. 이번 Phase의 각 스킬 실행 결과 리뷰
3. 대표에게 KPT 항목 확인 (추가/수정)

### 9단계: 다음 Phase 피드백 기록

KPT 회고 결과를 OPS-005로 정리하여 `docs/feedback/`에 저장한다.

### 10단계: 다중 관점 자체 검토 + 완료 보고

운영 결과를 3가지 관점에서 자체 검토하고 보고한다.

#### 안정성 관점

| 점검 항목 | 확인 |
|----------|------|
| P0/P1 인시던트가 모두 해결되었는가? | |
| 재발 방지 조치가 구체적이고 실행 가능한가? | |
| 회귀 테스트가 재현 케이스를 포함하는가? | |

#### 사용성 관점

| 점검 항목 | 확인 |
|----------|------|
| 수정이 다른 기능에 영향을 주지 않았는가? | |
| 사용자 관점에서 문제가 완전히 해결되었는가? | |

#### 학습 관점

| 점검 항목 | 확인 |
|----------|------|
| 근본 원인이 코드 결함을 넘어선 구조적 문제인가? | |
| learnings.jsonl에 교훈이 기록되었는가? | |
| 다음 Phase 피드백에 구조적 개선 사항이 포함되었는가? | |

## 의사결정 포인트

- P0 롤백 실행: 대표 승인 필수 (높음)
- 핫픽스 배포: 대표 승인 필수 (높음)
- 설계 결함으로 인한 스킬 회귀: 대표 승인 필수 (높음)
- 다음 Phase 피드백 확정: 대표 확인 (보통)

## 체크포인트

- 인시던트 분류 + 근본 원인 분석 완료 후 중간 보고
- 패치 + 회귀 테스트 완료 후 보고
- KPT 회고 완료 후 최종 보고

## 제약 사항

- 원인 미확인 상태에서 "일단 수정"하지 않는다 (5 Whys 완료 필수)
- 수정 범위를 최소화한다 (관련 없는 리팩토링 금지)
- 재현 불가 시 대표에게 보고하고 판단 요청
- 핫픽스는 대표 승인 필요 (의사결정 등급: 높음)
- P0/P1 인시던트는 Post-mortem 필수
- 5 Whys에서 3회 미만으로 "근본 원인"을 선언하지 않는다

## 완료 조건

- 설정된 관찰 기간 동안 P0/P1 장애 0건

- Post-mortem 작성 완료 (P0/P1 해당 시)
- KPT 회고 완료 및 OPS-005 기록
- 다중 관점 자체 검토 완료

## 실패/에스컬레이션 조건

- 재현 불가 시 대표에게 보고
- 동일 원인 3회 연속 실패 시 대표에게 에스컬레이션
- 긴급 장애(P0) 시 즉시 롤백 + 대표 보고
- 근본 원인이 설계 결함인 경우 design 스킬 회귀 제안
