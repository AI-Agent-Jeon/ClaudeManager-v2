### 0단계: 재개 확인 (계약 §0)

가장 먼저 `.orchestrator/status/develop.json`을 읽는다.

### 사전 점검 — 3단 검증 (계약 §1)

**L1 — 존재**

```bash
ls docs/design/ docs/design/api/ docs/design/data/ docs/design/ui/ 2>/dev/null
git branch --show-current
```

**L2 — 내용**

```bash
for f in docs/design/des-*.md docs/design/*/des-*.md; do [ -s "$f" ] || echo "EMPTY: $f"; done
# 구현에 필요한 최소 정보가 실제로 있는가
grep -cE '^\s*\|?\s*(GET|POST|PUT|PATCH|DELETE)\s' docs/design/api/des-002-api-spec.md   # 엔드포인트
grep -c 'erDiagram\|CREATE TABLE'                   docs/design/data/des-003-data-model.md  # ERD/스키마
grep -L 'Notion' docs/design/*.md docs/design/*/*.md
```

**설계서가 있어도 엔드포인트·스키마가 0건이면 구현할 수 없다.** 이 경우 L2 실패로 판정한다.

**L3 — 정합**

```bash
find docs/design -name 'des-*.md' | wc -l                                    # 실제
grep -oE 'DES-0[0-9]{2}' docs/plans/pln-002-phase1-plan.md | sort -u | wc -l # 계획
```

**판정**: L1 실패 → design 스킬 회귀 제안(진행 차단) · L2 실패 → 해당 설계서 회귀(진행 차단) · L3 편차 → 대표 보고(차단 없음)

`ls`가 성공했다는 이유만으로 통과 처리하지 않는다.

### 완료 후

project-agent 완료 시, **아래 검증을 통과하기 전에는 결과를 전달하지 않는다.**

**1. 결정 전파 잔여 확인 (계약 §2)**

승인·결정을 반영한 경우, 옛 표기가 남아 있지 않은지 전수 검색한다.

```bash
grep -rn "<바뀐 옛 표기>" docs/    # 출력이 비어야 통과
```

**"변경 예정" · "반영 대기" · "개정 대상" 상태로 종료하지 않는다.** 이 상태는 다음 세션에서 잊힌다.

**2. 이중 기록 검증 (계약 §3)**

```bash
find docs -name '*.md' ! -name 'CLAUDE.md' -exec grep -L 'Notion' {} +   # 출력이 비어야 통과
```

- Git `docs/` + Notion `02. 프로젝트 / ClaudeManager / 04. 개발` 양쪽에 존재
- 각 문서 헤더에 `> **원본**: [Notion {코드}](url) · Git 동기화 {날짜}`
- `docs/00-progress.md` 동기화 표 + Notion `00. 진행 상황` 갱신

**3. 보고 전 산출물 검증 (계약 §4)**

```bash
for f in <보고서 ## 산출물 칸의 경로 전건>; do
  [ -f "$f" ] && echo "OK   $f" || echo "MISSING $f"
done
```

`MISSING`이 하나라도 있으면 **보고를 중단하고** 누락을 채운다. 채울 수 없으면 산출물 칸에서 지우고 `## 미해결 사항`으로 옮긴다.

**4. 상태 파일 최종 갱신 (계약 §0)**

`.orchestrator/status/develop.json`에 `completed_steps` 전건과 `artifacts`(code / git / notion 3필드)를 기록한다.

**5. 결과 전달 및 전환**

1. 결과를 대표에게 전달
2. 다음 스킬 전환 정보에 따라:
   - 자동 → 해당 스킬 즉시 실행
   - 승인 필수 → 대표에게 실행 여부 확인

## 절차

### 1단계: 설계서 읽기 + 빌드 순서 확인

아래 문서를 읽고 구현 범위와 순서를 파악한다:

- DES-001 아키텍처 설계서 — 전체 구조, 모듈 경계
- DES-002 API 명세서 — 엔드포인트, 요청/응답 형식
- DES-003 데이터 모델 — 테이블, 관계, 스키마
- DES-008 파일/디렉토리 구조 — 생성할 파일 목록
- DES-009 코드 정의서 — Enum, 상수, 시스템 코드
- ANL-002 의존관계 맵 — **빌드 순서 (Layer 0→1→2→3)** 확인
- PLN-001 요구사항 정의서 — 수용 기준(Given-When-Then) 확인 (TDD 테스트 기반)

### 2단계: 개발 환경 설정

DES-008을 기반으로 프로젝트 골격을 구성한다:

1. 디렉토리 구조 생성 (DES-008 참조)
2. 패키지 매니저 초기화 + 의존성 설치 (ANL-004 기술 스택 기준)
3. 린터/포매터 설정 (src/CLAUDE.md 코딩 규칙 참조)
4. 테스트 프레임워크 설정 (tests/CLAUDE.md 참조)
5. Git feature 브랜치 생성 (아래 브랜치 전략 참조)

### 3단계: DB 마이그레이션 스크립트 작성

DES-003 데이터 모델을 기반으로 마이그레이션 스크립트를 작성한다:

- 파일명: `src/backend/migrations/{timestamp}-{name}.sql`
- 스키마 변경이 없으면 이 단계를 건너뛴다

### 4단계: TDD 사이클로 기능 구현

ANL-002의 빌드 순서(Layer 0→1→2→3)에 따라 모듈별로 구현한다.
각 모듈은 dev-sub에게 위임하며, **TDD 사이클**을 지시한다.

#### dev-sub 위임 시 전달 내용

```
구현 대상: {모듈/컴포넌트 이름}
참조 설계서: {DES-002 API 명세서의 해당 섹션 경로}
수용 기준: {PLN-001에서 해당 스토리의 Given-When-Then}
산출물 경로: {DES-008 기준 파일 위치}
테스트 경로: {tests/unit/ 하위 파일 위치}

TDD 사이클을 따라 구현하라:
1. Red — 수용 기준의 Given-When-Then을 단위 테스트로 작성, 실행하여 실패 확인
2. Green — 테스트를 통과하는 최소한의 코드 구현
3. Refactor — 중복 제거, 네이밍 개선, 구조 정리 (테스트 통과 유지)

커밋 단위: 기능 하나 완료 시 커밋 (아래 커밋 메시지 컨벤션 준수)
```

#### TDD 사이클 상세

```
┌─── Red ──────────────────────────────────┐
│ 1. Given-When-Then → 테스트 코드 변환     │
│ 2. 테스트 실행 → 실패 확인 (Red)          │
│    - 실패하지 않으면 테스트가 잘못된 것    │
└──────────────┬───────────────────────────┘
               ▼
┌─── Green ────────────────────────────────┐
│ 3. 테스트를 통과하는 최소 코드 작성       │
│ 4. 테스트 실행 → 통과 확인 (Green)        │
│    - 기존 테스트도 모두 통과해야 함        │
└──────────────┬───────────────────────────┘
               ▼
┌─── Refactor ─────────────────────────────┐
│ 5. 중복 제거, 네이밍 개선, 구조 정리      │
│ 6. 테스트 실행 → 통과 유지 확인           │
│ 7. Clean Code 체크 (아래 체크리스트)       │
└──────────────┬───────────────────────────┘
               ▼
           다음 스토리
```

### 5단계: 단위 테스트 커버리지 확인

전체 단위 테스트를 실행하고 커버리지를 확인한다:

```bash
# 프레임워크에 맞는 커버리지 명령 실행
# 예: npx jest --coverage, pytest --cov, go test -cover
```

**커버리지 기준**:

| 대상 | 최소 기준 |
|------|----------|
| Must 스토리 관련 코드 | 80% 이상 |
| Should 스토리 관련 코드 | 60% 이상 |
| 전체 | 70% 이상 |

미달 시 dev-sub에게 추가 테스트 작성을 요청한다.

### 6단계: Clean Code 자체 검토

구현 완료 후 아래 체크리스트로 코드 품질을 검토한다:

#### SOLID 원칙

| 원칙 | 점검 | 확인 |
|------|------|------|
| **S**ingle Responsibility | 각 모듈/함수가 하나의 책임만 갖는가? | |
| **O**pen/Closed | 확장에 열려 있고 수정에 닫혀 있는가? | |
| **L**iskov Substitution | 하위 타입이 상위 타입을 대체 가능한가? | |
| **I**nterface Segregation | 불필요한 인터페이스에 의존하지 않는가? | |
| **D**ependency Inversion | 구체 구현이 아닌 추상에 의존하는가? | |

#### DRY / KISS

| 원칙 | 점검 | 확인 |
|------|------|------|
| **DRY** | 중복 코드가 없는가? (3줄 이상 동일 패턴) | |
| **KISS** | 불필요하게 복잡한 구조가 없는가? | |
| 네이밍 | 변수/함수명이 의도를 명확히 드러내는가? | |
| 함수 크기 | 한 함수가 하나의 작업만 수행하는가? (20줄 이내 권장) | |
| 에러 처리 | 시스템 경계(API, DB)에서 에러를 적절히 처리하는가? | |

위반 항목이 있으면 dev-sub에게 리팩토링을 지시한다 (테스트 통과 유지).

### 7단계: CHANGELOG 업데이트

### 8단계: PR 자체 검토 체크리스트

PR 생성 전에 아래 체크리스트를 실행한다:

#### 보안

| 점검 | 확인 |
|------|------|
| 사용자 입력을 검증/이스케이프하는가? (XSS, SQL Injection) | |
| 인증/인가 누락된 엔드포인트가 없는가? | |
| 시크릿/API키가 코드에 하드코딩되어 있지 않은가? | |
| 에러 메시지에 내부 정보가 노출되지 않는가? | |

#### 성능

| 점검 | 확인 |
|------|------|
| N+1 쿼리 문제가 없는가? | |
| 불필요한 데이터 로딩이 없는가? (필요한 필드만 조회) | |
| 메모리 누수 가능성이 없는가? (이벤트 리스너, 타이머 정리) | |

#### 가독성

| 점검 | 확인 |
|------|------|
| 코딩 규칙(src/CLAUDE.md)을 준수하는가? | |
| 커밋 히스토리가 논리적 단위로 정리되어 있는가? | |
| 불필요한 console.log / print 문이 없는가? | |

위반 항목이 있으면 수정 후 PR을 생성한다.

PR 생성 후, 아래 3가지 관점에서 최종 자체 검토한다.

#### 코드 품질

| 점검 항목 | 확인 |
|----------|------|
| TDD 사이클을 모든 Must 스토리에 적용했는가? | |
| Clean Code 체크리스트를 통과했는가? | |
| 커버리지 기준을 충족하는가? | |

#### 설계 일치

| 점검 항목 | 확인 |
|----------|------|

| 데이터 모델이 DES-003과 일치하는가? | |

| 점검 항목 | 확인 |
|----------|------|
| 모든 수용 기준(Given-When-Then)에 대응하는 테스트가 있는가? | |
| 엣지 케이스(빈 값, 경계값, 에러)를 테스트했는가? | |
| 테스트가 독립적으로 실행되는가? (테스트 간 의존 없음) | |

## Git 브랜치 전략

### 브랜치 네이밍

```
feature/phase-{N}/{스토리코드}-{짧은설명}
```

**예시**:
- `feature/phase-1/FR-001-agent-crud`
- `feature/phase-1/FR-003-dashboard-status`

### 커밋 메시지 컨벤션 (Conventional Commits)

```
{type}({scope}): {설명}

{본문 (선택)}
```

| type | 용도 | 예시 |
|------|------|------|
| `feat` | 새 기능 | `feat(agent): 에이전트 생성 API 구현` |
| `fix` | 버그 수정 | `fix(ws): WebSocket 재연결 누락 수정` |
| `refactor` | 리팩토링 (기능 변경 없음) | `refactor(db): 쿼리 빌더 구조 개선` |
| `test` | 테스트 추가/수정 | `test(agent): 에이전트 생성 단위 테스트 추가` |
| `docs` | 문서 | `docs(changelog): v0.1.0 변경 이력 추가` |
| `chore` | 설정/빌드 | `chore: eslint + prettier 설정` |

- 개발 환경 설정 완료 후 보고

## 제약 사항

- 설계서에 없는 기능을 추가하지 않는다
- 단위 테스트 없이 완료하지 않는다 (TDD 필수)
- 동일 원인으로 3회 연속 실패 시 대표에게 에스컬레이션
- 배포/외부 API 연동은 대표 승인 없이 실행하지 않는다
- TDD의 Red 단계를 건너뛰지 않는다 (테스트 먼저 작성)
- PR 자체 검토 체크리스트를 건너뛰지 않는다
