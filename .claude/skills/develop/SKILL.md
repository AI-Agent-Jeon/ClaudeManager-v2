## Preamble (사전 점검)

실행 전 다음을 확인한다:
1. DES-001~009 존재 여부
   !`ls docs/design/ docs/design/api/ docs/design/data/ docs/design/ui/ 2>/dev/null`
2. 현재 브랜치 확인
   !`git branch --show-current`

누락 산출물이 있으면 Agent에게 보고하고 design 스킬 회귀를 제안한다.

## 입력 (이전 스킬에서 받는 바통)

- DES-001 아키텍처 설계서
- DES-002 API 명세서
- DES-003 데이터 모델 (ERD)
- DES-005 스토리보드
- DES-006 화면 명세서
- DES-007 상태 흐름도
- DES-008 파일/디렉토리 구조
- DES-009 코드 정의서 (시스템)

## 출력 (다음 스킬에 넘기는 바통)

- DEV-001 소스코드
- DEV-002 단위 테스트 코드
- DEV-003 PR (생성 상태 — 머지는 test 통과 후)
- DEV-004 변경 이력 (CHANGELOG)
- DEV-005 DB 마이그레이션 스크립트

## 필요 권한

- 도구: Read, Write, Edit, Bash, Grep, Glob
- Sub-Agent: dev-sub (코딩 + 단위 테스트)

## 절차

1. 설계서와 API 명세 읽기
2. 구현 순서 결정: 의존관계 기반 (의존 없는 것 먼저)
3. dev-sub에게 코딩 위임
4. 단위 테스트 작성: dev-sub가 구현과 함께 작성
5. 단위 테스트 실행: 실패 시 dev-sub에게 수정 요청
6. CHANGELOG 업데이트
7. DB 마이그레이션 스크립트 작성 (스키마 변경 시)
8. PR 생성
9. 완료 보고

## 의사결정 포인트

- 설계서에 없는 판단이 필요한 경우: 대표에게 보고 (보통)
- 배포/외부 API 연동: 대표 승인 필수 (높음)

## 체크포인트

- 핵심 모듈 구현 완료 후 중간 보고
- 단위 테스트 통과 후 PR 생성 전 확인

## 제약 사항

- 설계서에 없는 기능을 추가하지 않는다
- 단위 테스트 없이 완료하지 않는다
- 동일 원인으로 3회 연속 실패 시 대표에게 에스컬레이션
- 배포/외부 API 연동은 대표 승인 없이 실행하지 않는다

## 완료 조건

- PR 생성 + 단위 테스트 통과 (PR 머지는 test 통과 후)

## 실패/에스컬레이션 조건

- 동일 원인 3회 연속 실패 시 대표에게 에스컬레이션
- 설계 오류 발견 시 design 스킬로 회귀 요청

## 완료 후 액션

스킬 완료 시:
1. 완료 요약 (산출물 목록 + PR 링크)
2. docs/00-progress.md 갱신
3. 스킬 전환 모드 확인 → 자동이면 test 스킬 시작, 승인이면 대표에게 제안
