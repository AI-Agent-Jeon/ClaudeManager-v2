## 디스패치

> **필수 선행**: 이 스킬을 실행하기 전에 `.claude/skills/_shared/execution-contract.md`(실행 계약)를 읽는다.
> 아래는 그 계약의 이 스킬용 요약이다. **상세 규칙과 금지 사항은 계약 문서가 기준이며, 충돌 시 계약이 우선한다.**

### 0단계: 재개 확인 (계약 §0)

가장 먼저 `.orchestrator/status/deploy.json`을 읽는다.

- 없으면 생성하고 `current_step: 1`로 시작한다
- 있으면 `completed_steps`의 **다음 단계부터** 재개한다
- **`completed_steps`에 없는 단계를 수행했다고 가정하지 않는다**
- 각 단계 종료 시 즉시 갱신한다 (몰아서 기록 금지)

### 사전 점검 — 3단 검증 (계약 §1)

**L1 — 존재**

```bash
gh pr list --state merged --limit 5 2>/dev/null
ls docs/test-reports/ 2>/dev/null
git branch --show-current
```

**L2 — 내용**

```bash
for f in docs/test-reports/tst-*.md docs/test-reports/*/tst-*.md; do [ -s "$f" ] || echo "EMPTY: $f"; done
# 테스트 결과가 "통과"로 실제 기록되어 있는가 — 미결 결함이 남아 있으면 배포 불가
grep -rn "실패\|FAIL\|미해결\|블로커" docs/test-reports/
grep -L 'Notion' docs/test-reports/*.md docs/test-reports/*/*.md
```

**미해결 결함이 하나라도 남아 있으면 L2 실패다.** 배포는 등급 **높음**이므로 여기서 차단한다.

**L3 — 정합**

TST 산출물 개수와 계획(TST-001~007)을 대조한다. 성능·보안 검토가 조건부 생략됐다면 그 사유가 문서에 기록되어 있어야 한다.

**판정**: L1·L2 실패 → test 스킬 회귀 제안(진행 차단) · L3 편차 → 대표 보고(차단 없음)

### 위임

사전 점검 통과 시, project-agent를 생성한다:
- subagent_type: `project-agent`
- 전달: 스킬 `deploy`, 경로 `.claude/skills/deploy/SKILL.md`
- **함께 전달**: `.claude/skills/_shared/execution-contract.md` 경로와 "이 계약을 먼저 읽고 실행하라"는 지시

### 완료 후

project-agent 완료 시, **아래 검증을 통과하기 전에는 결과를 전달하지 않는다.**

**1. 결정 전파 잔여 확인 (계약 §2)**

승인·결정을 반영한 경우, 옛 표기가 남아 있지 않은지 전수 검색한다.

```bash
grep -rn "<바뀐 옛 표기>" docs/    # 출력이 비어야 통과
```

**"변경 예정" · "반영 대기" · "개정 대상" 상태로 종료하지 않는다.** 이 상태는 다음 세션에서 잊힌다.

**2. 이중 기록 검증 (계약 §3)**

```bash
find docs -name '*.md' ! -name 'CLAUDE.md' -exec grep -L 'Notion' {} +   # 출력이 비어야 통과
```

- Git `docs/` + Notion `02. 프로젝트 / ClaudeManager / 06. 배포` 양쪽에 존재
- 각 문서 헤더에 `> **원본**: [Notion {코드}](url) · Git 동기화 {날짜}`
- `docs/00-progress.md` 동기화 표 + Notion `00. 진행 상황` 갱신

**3. 보고 전 산출물 검증 (계약 §4)**

```bash
for f in <보고서 ## 산출물 칸의 경로 전건>; do
  [ -f "$f" ] && echo "OK   $f" || echo "MISSING $f"
done
```

`MISSING`이 하나라도 있으면 **보고를 중단하고** 누락을 채운다. 채울 수 없으면 산출물 칸에서 지우고 `## 미해결 사항`으로 옮긴다.

**4. 상태 파일 최종 갱신 (계약 §0)**

`.orchestrator/status/deploy.json`에 `completed_steps` 전건과 `artifacts`(code / git / notion 3필드)를 기록한다.

**5. 결과 전달 및 전환**

1. 결과를 대표에게 전달
2. 다음 스킬 전환 정보에 따라:
   - 자동 → 해당 스킬 즉시 실행
   - 승인 필수 → 대표에게 실행 여부 확인

## 절차

### 1단계: 테스트 결과 확인

TST-002(테스트 결과 리포트)와 TST-004(버그 목록)를 읽고 배포 가능 여부를 판단한다.

**배포 가능 기준**:

| 항목 | 기준 | 미충족 시 |
|------|------|----------|
| 치명(Critical) 결함 | 0건 | 배포 불가 — develop 회귀 |
| 높음(High) 결함 | 0건 | 배포 불가 — develop 회귀 |
| 보통(Medium) 결함 | 허용 (기록 후 진행) | 릴리스 노트에 "알려진 이슈"로 기록 |
| 단위 테스트 통과율 | 100% | 배포 불가 |
| PR 머지 상태 | 완료 | 배포 불가 — test 회귀 |

### 2단계: Pre-flight 체크리스트 실행

배포 전 환경을 구조적으로 점검한다. 각 항목의 결과를 ✅/❌로 기록한다.

```markdown
## Pre-flight 체크리스트

### 환경 변수
- [ ] 필수 환경 변수 목록 확인 (.env.example 또는 설정 문서 기준)
- [ ] 각 환경 변수에 값이 설정되어 있는가
- [ ] 시크릿 값이 코드에 하드코딩되어 있지 않은가

### 의존성
- [ ] package.json / requirements.txt 등 의존성 파일 최신인가
- [ ] lock 파일 (package-lock.json 등) 커밋되어 있는가
- [ ] 의존성 설치 성공: `npm install` 또는 해당 명령 실행
- [ ] 보안 취약 의존성 확인: `npm audit` 또는 해당 명령

### DB / 마이그레이션
- [ ] 미적용 마이그레이션 스크립트 존재 여부 확인
- [ ] 마이그레이션 실행 순서 확인 (타임스탬프 기준)
- [ ] 마이그레이션 롤백 가능 여부 확인

### 포트 / 프로세스
- [ ] 사용할 포트 충돌 확인: `lsof -i :{PORT}`
- [ ] 이전 프로세스 정리 필요 여부 확인

### 빌드 산출물
- [ ] 빌드 출력 디렉토리 정리 (이전 빌드 잔여물 제거)
```

**Pre-flight 실패 시**: 실패 항목을 대표에게 보고하고 해결 방안을 제시한다. 환경 변수 누락이나 의존성 문제는 자율 해결(낮음), 마이그레이션 문제는 대표 확인(보통).

### 3단계: 빌드 실행 + 빌드 검증

```markdown
## 빌드 단계 체크리스트

| 단계 | 명령 | 성공 기준 | 실패 시 |
|------|------|----------|---------|
| 의존성 설치 | `npm install` 등 | exit code 0 | 의존성 문제 해결 후 재시도 |
| 빌드 | `npm run build` 등 | exit code 0 + 산출물 존재 | 빌드 에러 로그 → develop 회귀 |
| 타입 체크 | `npm run typecheck` 등 | exit code 0 | 타입 에러 → develop 회귀 |
| 린트 | `npm run lint` 등 | exit code 0 | 자동 수정 시도 → 실패 시 develop 회귀 |
```

각 단계는 순차 실행하며, 실패 시 이후 단계를 진행하지 않는다.

### 4단계: Smoke Test 정의 작성

배포 후 실행할 Smoke Test 항목을 미리 정의한다. DES-005(스토리보드)와 PLN-001(수용 기준)을 참고하여 핵심 사용자 흐름을 검증 대상으로 선정한다.

```markdown
## Smoke Test 정의

### 인프라 검증
| ID | 항목 | 검증 방법 | 성공 기준 |
|----|------|----------|----------|
| SM-01 | 서버 기동 | 프로세스 상태 확인 | 프로세스 alive |
| SM-02 | Health 엔드포인트 | `curl /health` | HTTP 200 + status: ok |
| SM-03 | DB 연결 | Health 응답의 db 필드 | connected: true |
| SM-04 | WebSocket 연결 | WS 핸드셰이크 | 연결 성공 |

### 핵심 기능 검증 (Walking Skeleton 기반)
| ID | 항목 | 검증 방법 | 성공 기준 |
|----|------|----------|----------|
| SM-05 | {핵심 기능 1} | {API 호출 또는 UI 동작} | {기대 결과} |
| SM-06 | {핵심 기능 2} | ... | ... |
```

**Smoke Test 기준**: Walking Skeleton의 Must 스토리에서 추출한 핵심 흐름을 최소 1회 관통하는 시나리오.

### 5단계: 대표 배포 승인 요청

Pre-flight 결과, 빌드 결과, Smoke Test 정의를 대표에게 제출하고 배포 승인을 요청한다 (AskUserQuestion, 의사결정 등급: **높음**).

**승인 요청 포함 사항**:
- Pre-flight 체크리스트 결과 요약 (✅ 전체 통과 / ⚠️ 허용 항목 목록)
- 빌드 결과 (성공/실패 + 산출물)
- Smoke Test 항목 목록
- 알려진 이슈 (Medium 결함 목록)
- 롤백 계획 요약

### 6단계: 배포 실행

대표 승인 후 배포를 실행한다.

```markdown
## 배포 실행 체크리스트

| 순서 | 작업 | 롤백 지점 |
|------|------|----------|
| 1 | DB 마이그레이션 실행 | 마이그레이션 롤백 스크립트 |
| 2 | 이전 프로세스 종료 | 이전 버전 재기동 |
| 3 | 새 버전 프로세스 시작 | 이전 버전 재기동 |
| 4 | Smoke Test 실행 | 이전 버전 재기동 + 마이그레이션 롤백 |
```

각 단계 실패 시 해당 롤백 지점으로 복구한다.

### 7단계: Smoke Test 실행 + 결과 판정

4단계에서 정의한 항목을 실행하고 결과를 기록한다.

**판정 기준**:

| 결과 | 조건 | 행동 |
|------|------|------|
| ✅ PASS | 인프라 검증 전체 통과 + 핵심 기능 전체 통과 | 배포 성공, 8단계 건너뜀 |
| ⚠️ PARTIAL | 인프라 통과 + 핵심 기능 일부 실패 | 대표에게 보고, 계속/롤백 결정 요청 |
| ❌ FAIL | 인프라 실패 또는 핵심 기능 다수 실패 | 즉시 롤백 (8단계) |

### 8단계: 롤백 판단 (실패 시)

아래 **롤백 트리거 조건** 중 하나라도 해당되면 롤백을 실행한다:

```markdown
## 롤백 트리거 조건

| 트리거 | 기준 | 자동/수동 |
|--------|------|----------|
| 서버 미기동 | 프로세스 시작 후 30초 내 Health 응답 없음 | 자동 롤백 |
| DB 연결 실패 | Health 응답에서 db: disconnected | 자동 롤백 |
| 핵심 기능 실패 | Smoke Test SM-05~SM-xx 중 50% 이상 실패 | 자동 롤백 |
| 핵심 기능 일부 실패 | Smoke Test SM-05~SM-xx 중 50% 미만 실패 | 대표 판단 |
| 에러 로그 급증 | 배포 후 5분 내 에러 로그 10건 이상 | 대표 보고 후 판단 |
```

**롤백 절차**:

```markdown
## 롤백 절차

1. 새 프로세스 종료
2. DB 마이그레이션 롤백 (해당 시)
3. 이전 버전 프로세스 재기동
4. 이전 버전 Smoke Test 실행 (복구 확인)
5. 대표에게 롤백 결과 보고 (원인 + 재배포 계획)
```

**긴급 롤백 (서버 미기동, DB 실패)**: 대표 승인 없이 자동 실행 후 보고.
**비긴급 롤백 (기능 일부 실패)**: 대표 확인 후 실행 (보통).

### 9단계: 릴리스 노트 작성

**Keep a Changelog** 형식으로 릴리스 노트를 작성한다. DEV-004(CHANGELOG)와 TST-004(버그 목록)를 참조한다.

### 10단계: 완료 보고

DPL-001~004를 docs/에 저장하고 대표에게 최종 보고한다.

## 의사결정 포인트

- 배포 실행 승인: 대표 승인 필수 (높음)
- 비긴급 롤백: 대표 확인 (보통)
- 긴급 롤백 (서버 미기동, DB 실패): 자동 실행 후 보고 (낮음 → 사후 보고)
- Pre-flight 실패 항목 해결: 환경/의존성은 자율(낮음), 마이그레이션은 대표 확인(보통)

## 체크포인트

- Pre-flight + 빌드 완료 후 중간 보고 (배포 승인 요청 전)
- Smoke Test 완료 후 최종 보고

## 제약 사항

- 테스트 미통과 상태에서 배포하지 않는다
- 롤백 계획을 배포 전에 반드시 준비한다
- 배포 준비(Pre-flight, 빌드)는 자동 수행
