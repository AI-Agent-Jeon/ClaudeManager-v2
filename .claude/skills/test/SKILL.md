### 사전 점검 — 3단 검증 (계약 §1)

**L1 — 존재**

```bash
ls src/ tests/unit/ 2>/dev/null
gh pr list --state open --limit 5 2>/dev/null
git branch --show-current
```

**L2 — 내용**

```bash
# 테스트 파일이 있다는 것과 테스트가 있다는 것은 다르다
find tests/ -name '*test*' -size -1c 2>/dev/null          # 빈 테스트 파일
grep -rc 'it(\|test(\|def test_\|func Test' tests/ | grep ':0$'   # 케이스 0건인 파일
# 단위 테스트가 실제로 통과하는가 (프레임워크에 맞게 조정)
```

**케이스가 0건인 테스트 파일은 L2 실패로 판정한다.** 존재만으로 통과시키지 않는다.

**L3 — 정합**

```bash
grep -oE 'DEV-00[0-9]' docs/plans/pln-002-phase1-plan.md | sort -u | wc -l
```

구현된 요구사항 코드와 PLN-002 Must 목록을 대조해 **누락된 스토리**를 찾는다.

## 테스트 피라미드 가이드라인

테스트 비율을 아래 피라미드로 관리한다:

```
        ╱  E2E  ╲          ~10%  (인수 테스트, 시나리오 테스트)
       ╱─────────╲
      ╱ Integration╲       ~20%  (통합 테스트, API 테스트)
     ╱───────────────╲
    ╱   Unit Tests    ╲    ~70%  (단위 테스트)
   ╱───────────────────╲
```

| 계층 | 비율 | 특성 | 실행 주체 |
|------|------|------|----------|
| Unit | ~70% | 빠름, 격리, 단일 함수/모듈 | dev-sub (develop 단계), test-sub (검증) |
| Integration | ~20% | API 호출, DB 연동, 모듈 간 협력 | test-sub |
| E2E | ~10% | 사용자 시나리오 전체 흐름 | test-sub |

**커버리지 기준**:
- Must 스토리: 단위 테스트 커버리지 **80% 이상**
- Should 스토리: 단위 테스트 커버리지 **60% 이상**
- 전체 통합 테스트: Walking Skeleton 흐름 **100% 커버**

### 2단계: 테스트 케이스 설계 — BVA + EP

PLN-001의 Given-When-Then 수용 기준을 테스트 케이스로 변환한다.

#### Given-When-Then → 테스트 케이스 변환 규칙

```
Given [사전 조건]  →  테스트 setup (fixtures, mocks, 초기 상태)
When  [행동]       →  테스트 action (함수 호출, API 요청, UI 동작)
Then  [기대 결과]  →  테스트 assertion (expect, assert)
```

#### 경계값 분석 (BVA) 적용

각 수용 기준에서 경계가 되는 값을 식별하고 테스트 케이스를 추가한다.

**예시**: "Given 에이전트가 5개 이하일 때 When 에이전트를 생성하면 Then 성공한다"

| 테스트 | 입력 | 기대 결과 | 기법 |
|--------|------|----------|------|
| 정상 — 0개 상태 | count=0 | 성공 | BVA (하한) |
| 정상 — 4개 상태 | count=4 | 성공 | EP (유효 클래스) |
| 경계 — 5개 상태 | count=5 | 성공 | BVA (상한) |
| 경계 — 6개 상태 | count=6 | 실패/에러 | BVA (상한+1) |
| 비정상 — 음수 | count=-1 | 에러 | EP (무효 클래스) |

#### 동치 분할 (EP) 적용

입력 도메인을 유효/무효 클래스로 나누고, 각 클래스에서 대표값 하나를 테스트한다.

```
유효 클래스: [0..5]  →  대표값 3
무효 클래스: [-∞..-1] →  대표값 -1
무효 클래스: [6..+∞]  →  대표값 10
무효 클래스: null/undefined → 대표값 null
```

review-sub에게 위임한다.

| # | OWASP 항목 | 점검 내용 |

| A01 | Broken Access Control | 인가 없이 접근 가능한 API/페이지 |

### 7단계: 성능 테스트 (조건부)

NFR 스토리가 있거나, 변경이 요청 처리 경로에 영향을 줄 때 실행한다.

**3단계 성능 테스트 방법론**:

| 단계 | 목적 | 방법 |
|------|------|------|
| **기준선(Baseline)** | 현재 성능 수치 확보 | 단일 요청 응답 시간, 메모리 사용량 측정 |
| **부하(Load)** | 정상 사용 시뮬레이션 | 예상 동시 사용자 수준으로 부하, 응답 시간 유지 확인 |
| **스트레스(Stress)** | 한계 확인 | 부하를 점진 증가, 성능 저하 시점 및 복구 확인 |

**MVP 성능 기준** (단일 사용자, 로컬):
- API 응답: 200ms 이내 (p95)
- 페이지 로드: 1초 이내
- WebSocket 메시지 지연: 100ms 이내

### 8단계: 인수 테스트 (UAT)

스토리보드(DES-005)와 수용 기준(PLN-001)을 기반으로 사용자 관점 검증:
- 각 Must 스토리의 Given-When-Then 수용 기준 전부 통과 확인
- Walking Skeleton 전체 흐름 실행 가능 확인
- 에러 상황에서의 사용자 안내 확인

### 9단계: 버그 수정 루프

발견된 결함을 심각도별로 처리한다:

| 심각도 | 처리 |
|--------|------|
| 치명/높음 | dev-sub에게 수정 위임 → 재테스트 필수 |
| 보통 | dev-sub에게 수정 위임 → 재테스트 권장 |
| 낮음 | 버그 목록에 기록, Phase 내 또는 다음 Phase에서 수정 |

**수정-재테스트 루프**: 동일 원인 3회 연속 실패 시 대표에게 에스컬레이션.

## 의사결정 포인트

- 치명/높음 버그 발견 시: 수정 후 재테스트 필수
- 성능/보안 기준 미달 시: 대표에게 보고 (보통)
- 커버리지 기준 미달 시: 대표에게 보고 후 판단 (보통)

## 체크포인트

- 통합 테스트 완료 후 중간 보고 (결과 + 버그 목록)
- 코드 리뷰 + 보안 검토 완료 후 결과 공유
- 다중 관점 검토 후 최종 보고

## 제약 사항

- review-sub는 코드를 직접 수정하지 않는다 (리뷰만)
- test-sub, review-sub는 Write 불가 — 결과는 Agent가 문서화
- 치명/높음 발견 시 "수정 후 재테스트 필요"로 판정
- 수정-재테스트 반복은 동일 원인 3회 연속 실패 시 대표에게 에스컬레이션
- test-sub과 review-sub는 독립 Task로 병렬 실행 가능
- 테스트 커버리지 기준 미달 시 PR 머지하지 않는다 (대표 예외 승인 제외)
