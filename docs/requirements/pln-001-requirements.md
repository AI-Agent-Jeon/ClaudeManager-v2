## 문제 정의

### 수요 현실

1인 CEO가 다수의 AI 에이전트(Claude Code)를 활용해 프로젝트를 운영 중이나, 다음 5가지 고통이 존재한다.

| # | 고통 | 구체적 상황 | 영향 |
|---|------|-----------|------|
| 1 | 에이전트마다 별도 터미널 직접 관리 | 동시 3~5개 에이전트 실행 시 터미널 전환 반복 | 상태 누락, 감독 불가 |
| 2 | 승인 프로세스 부재 | 위험 작업(배포, 데이터 변경) 무단 실행 가능 | 장애 위험 |
| 3 | 산출물 흩어짐 | 프로세스 미표준화, 이력 추적 불가 | 재작업, 품질 저하 |
| 4 | 장애 시 수동 복구 | 진행 중 작업 유실, 복구 시간 불예측 | 생산성 손실 |
| 5 | 비용 파악 불가 | API 사용량/비용 산재, 예산 초과 인지 지연 | 비용 낭비 |

### 현재 대안과 비용

- 각 에이전트를 별도 터미널 탭에서 수동 관리
- 상태 확인: 터미널 간 전환하며 출력 확인 (시간 소모, 컨텍스트 손실)
- 승인: 에이전트가 물어볼 때만 인지 (놓칠 수 있음)
- 기록: 터미널 스크롤백에 의존 (영속성 없음)
- 비용: Anthropic 대시보드에서 수동 확인 (프로젝트별 구분 불가)

### 최소 범위 (Phase 1)

Phase 1은 이후 모든 기능의 기반이 되는 인프라를 구축한다.

1. 로컬 백엔드 서버 (웹 UI, CLI의 통신 기반)
2. CLI-백엔드 연동 (터미널에서 시스템 접근)
3. 단일 사용자 인증 (보안 기초)
4. 프로젝트 CRUD (관리 단위 확립)
5. Agent/Task 상태 저장소 (모니터링 기반)
6. 상태 변경 로그 (감사 추적 기초)
7. Agent 프로세스 감지 (자동 등록 기초)

### 전제와 리스크

| 전제 | 근거 | 틀리면? |
|------|------|--------|
| 1인 사용자, 로컬 실행 | MVP 범위 명시 | 다중 사용자 시 인증/권한 재설계 필요 |
| SQLite로 충분 | 동시 접속 1명, 데이터 소량 | 동시 쓰기 병목 시 PostgreSQL 전환 (마이그레이션 체계로 대응) |
| REST + WebSocket | REST=CRUD, WS=실시간 (Phase 2) | gRPC 등 대안 검토, 하지만 1인 사용에 과잉 |
| Claude Code 에이전트만 | 현재 사용 도구 | 다른 AI 도구 추가 시 프로세스 감지 확장 필요 |
| 프레임워크 미결정 | analyze 단계에서 ADR로 결정 | 결정 지연은 리스크 아님 (Phase 1 범위 내 충분) |

## 선택한 접근법

### 접근법 A: API-First 기반 구축

- **핵심**: REST API 스펙을 먼저 정의하고, 스펙 기준으로 백엔드 구현
- **범위**: 모든 Phase 1 항목을 API 계층 중심으로 구축
- **장점**: API 계약 확정 → Phase 2 웹 UI가 동일 API 사용, 프론트-백 병렬 개발 가능
- **리스크**: 실사용 전 과잉 설계 가능, API 변경 비용 증가
- **예상 규모**: 스토리 17개, 복잡도 중

### 접근법 B: Walking Skeleton 점진 구축 (추천)

- **핵심**: 서버→인증→프로젝트→상태→CLI 최소 경로를 먼저 구현, 나머지 점진 추가
- **범위**: 핵심 흐름 먼저 동작 검증, 이후 확장
- **장점**: 빠른 동작 확인, 아키텍처 검증, 피드백 빠름, MVP 철학 부합
- **리스크**: 초기 구조가 확장 시 리팩터링 필요할 수 있음
- **예상 규모**: Walking Skeleton 7 스토리 → 나머지 10 스토리

### 접근법 C: 데이터 모델 중심

- **핵심**: 상태 모델(8장)을 SQLite 스키마로 먼저 확정, 그 위에 API/CLI 구축
- **범위**: 데이터 무결성 우선, 상태 전이 검증 후 서비스 계층
- **장점**: 견고한 데이터 기반, 상태 모델이 전체 시스템의 핵심이므로 조기 검증
- **리스크**: 실사용 없이 스키마 과잉 설계, 불필요한 정규화
- **예상 규모**: 스토리 17개, 복잡도 중~높

### 추천

- **추천안**: 접근법 B (Walking Skeleton 점진 구축)
- **근거**: Phase 1은 "기반 구축"이므로 전체 스택이 동작하는 최소 경로를 빠르게 확인하는 것이 핵심. 과잉 설계보다 동작하는 코드를 먼저 만들고 점진 확장하는 것이 1인 개발에 적합
- **기각 사유**
  - A: Phase 2 UI 전에 API 스펙을 완벽히 정의하면, 실 사용 피드백 없이 변경 비용만 증가
  - C: 상태 모델은 중요하지만 실사용 없이 스키마만 만들면 실제 필요와 괴리 가능

## Story Map

### [시스템 기반] Activity 1

#### [백엔드 서버 구축] Task 1.1

**FR-001 백엔드 서버 시작/종료**
- **스토리**: 대표로서 로컬 백엔드 서버를 시작/종료하여 웹 UI와 CLI의 통신 기반을 마련한다
- **분류**: FR / **우선순위**: Must
- 수용 기준
  - [ ] Given 서버 실행 파일이 존재할 때 When 서버 시작 명령을 실행하면 Then 지정 포트에서 HTTP 요청을 수신한다
  - [ ] Given 서버가 실행 중일 때 When 종료 신호(SIGTERM)를 보내면 Then 진행 중인 요청을 완료한 후 정상 종료한다
  - [ ] Given 서버가 시작될 때 When DB 연결에 실패하면 Then 에러 메시지와 함께 시작이 중단된다

**NFR-001 API 응답 성능**
- **스토리**: 대표로서 API 응답이 3초 이내로 돌아와 쾌적하게 사용한다
- **분류**: NFR / **우선순위**: Should
- 수용 기준
  - [ ] Given 서버가 정상 가동 중일 때 When 임의의 CRUD API 요청을 보내면 Then 3초 이내에 응답한다

#### [데이터 저장소 구축] Task 1.2

**DAT-001 SQLite 데이터 영속 저장**
- **스토리**: 대표로서 데이터가 SQLite에 영속 저장되어 서버 재시작 후에도 유지된다
- **분류**: DAT / **우선순위**: Must
- 수용 기준
  - [ ] Given 프로젝트를 생성한 후 When 서버를 재시작하면 Then 생성한 프로젝트가 그대로 조회된다
  - [ ] Given SQLite 파일이 없을 때 When 서버를 최초 시작하면 Then 초기 스키마가 적용된 DB 파일이 생성된다

**DAT-002 DB 마이그레이션 체계**
- **스토리**: 대표로서 DB 스키마가 마이그레이션으로 관리되어 안전하게 스키마를 변경한다
- **분류**: DAT / **우선순위**: Must
- 수용 기준
  - [ ] Given 새로운 마이그레이션 파일이 추가되었을 때 When 서버를 시작하면 Then 미적용 마이그레이션이 순서대로 실행된다
  - [ ] Given 마이그레이션이 실패할 때 When 에러가 발생하면 Then 해당 마이그레이션은 롤백되고 에러가 보고된다

### [접근 제어] Activity 2

#### [사용자 인증] Task 2.1

**FR-002 토큰 기반 인증**
- **스토리**: 대표로서 토큰 기반으로 로그인하여 시스템에 안전하게 접근한다
- **분류**: FR / **우선순위**: Must
- 수용 기준
  - [ ] Given 올바른 인증 정보를 가지고 있을 때 When 로그인 요청을 보내면 Then 인증 토큰이 발급된다
  - [ ] Given 잘못된 인증 정보를 가지고 있을 때 When 로그인 요청을 보내면 Then 401 에러가 반환된다
  - [ ] Given 인증 토큰이 만료되었을 때 When API 요청을 보내면 Then 401 에러와 재로그인 안내가 반환된다

**NFR-002 API 인증 미들웨어**
- **스토리**: 대표로서 인증 없는 API 접근이 차단되어 보안이 유지된다
- **분류**: NFR / **우선순위**: Must
- 수용 기준
  - [ ] Given 인증 토큰 없이 When 보호된 API에 요청하면 Then 401 Unauthorized가 반환된다
  - [ ] Given 유효한 인증 토큰으로 When 보호된 API에 요청하면 Then 정상 응답이 반환된다

### [프로젝트 관리] Activity 3

#### [프로젝트 CRUD] Task 3.1

**FR-003 프로젝트 생성**
- **스토리**: 대표로서 프로젝트를 생성하여 작업을 시작한다
- **분류**: FR / **우선순위**: Must
- 수용 기준
  - [ ] Given 인증된 상태일 때 When 프로젝트 이름과 설명을 제공하면 Then 새 프로젝트가 '준비' 상태로 생성된다
  - [ ] Given 동일 이름의 프로젝트가 존재할 때 When 같은 이름으로 생성하면 Then 중복 에러가 반환된다

**FR-004 프로젝트 목록 조회**
- **스토리**: 대표로서 프로젝트 목록을 조회하여 현황을 파악한다
- **분류**: FR / **우선순위**: Must
- 수용 기준
  - [ ] Given 프로젝트가 3개 존재할 때 When 목록 조회를 요청하면 Then 3개 프로젝트의 이름, 상태, 생성일이 반환된다
  - [ ] Given 프로젝트가 없을 때 When 목록 조회를 요청하면 Then 빈 목록이 반환된다

**FR-005 프로젝트 상세 조회**
- **스토리**: 대표로서 프로젝트 상세를 확인하여 정보를 파악한다
- **분류**: FR / **우선순위**: Should
- 수용 기준
  - [ ] Given 프로젝트가 존재할 때 When 상세 조회를 요청하면 Then 이름, 설명, 상태, 생성일, Agent 목록이 반환된다
  - [ ] Given 존재하지 않는 프로젝트 ID로 When 상세 조회하면 Then 404 에러가 반환된다

**FR-006 프로젝트 상태 변경**
- **스토리**: 대표로서 프로젝트 상태를 변경하여 진행을 관리한다
- **분류**: FR / **우선순위**: Must
- 수용 기준
  - [ ] Given 프로젝트가 '준비' 상태일 때 When 상태를 '진행 중'으로 변경하면 Then 상태가 갱신되고 변경 로그가 기록된다
  - [ ] Given 허용되지 않은 상태 전환일 때 When 상태 변경을 요청하면 Then 에러와 허용 전환 목록이 반환된다

### [상태 추적] Activity 4

#### [Agent/Task 상태 저장] Task 4.1

**FR-007 Agent 상태 CRUD**
- **스토리**: 대표로서 Agent 상태가 저장되어 현재 상황을 파악한다
- **분류**: FR / **우선순위**: Must
- 수용 기준
  - [ ] Given Agent가 등록될 때 When 상태 저장을 요청하면 Then Agent 정보(이름, 유형, 상태, 프로젝트ID)가 DB에 저장된다
  - [ ] Given Agent 상태가 변경될 때 When 상태 갱신을 요청하면 Then 상태가 갱신되고 이전 상태가 로그에 기록된다
  - [ ] Given 프로젝트 ID로 When Agent 목록을 조회하면 Then 해당 프로젝트의 모든 Agent 정보가 반환된다

**FR-008 Task 상태 CRUD**
- **스토리**: 대표로서 Task 상태가 저장되어 작업 진행을 추적한다
- **분류**: FR / **우선순위**: Must
- 수용 기준
  - [ ] Given Agent에 Task가 할당될 때 When Task 생성을 요청하면 Then Task 정보(이름, 상태, AgentID)가 DB에 저장된다
  - [ ] Given Task 상태가 변경될 때 When 상태 갱신을 요청하면 Then 상태가 갱신되고 변경 로그가 기록된다

#### [상태 변경 로그] Task 4.2

**FR-009 상태 변경 이력**
- **스토리**: 대표로서 상태 변경 이력을 조회하여 과거 활동을 확인한다
- **분류**: FR / **우선순위**: Must
- 수용 기준
  - [ ] Given 프로젝트/Agent/Task 상태가 변경될 때 When 변경이 발생하면 Then 엔티티 유형, ID, 이전 상태, 새 상태, 타임스탬프가 자동 기록된다
  - [ ] Given 특정 엔티티의 When 상태 변경 이력을 조회하면 Then 시간순으로 모든 변경 내역이 반환된다

**FR-010 행동(감사) 로그**
- **스토리**: 대표로서 행동 로그가 기록되어 감사 추적이 가능하다
- **분류**: FR / **우선순위**: Should
- 수용 기준
  - [ ] Given 사용자가 API를 호출할 때 When 요청이 처리되면 Then 행동 유형, 대상, 타임스탬프, 결과가 로그에 기록된다
  - [ ] Given 행동 로그가 존재할 때 When 필터(기간, 유형)로 조회하면 Then 조건에 맞는 로그가 반환된다

#### [CLI-백엔드 통신] Task 5.1

**INT-001 CLI-백엔드 HTTP 통신**
- **스토리**: 대표로서 CLI에서 백엔드 API를 호출하여 터미널에서도 시스템을 사용한다

**INT-002 CLI 프로젝트 관리 명령어**
- **스토리**: 대표로서 CLI에서 프로젝트를 관리하여 빠르게 작업한다
- **분류**: INT / **우선순위**: Should
- 수용 기준
  - [ ] Given CLI에서 인증된 상태일 때 When 프로젝트 목록 명령을 실행하면 Then 프로젝트 목록이 테이블 형태로 표시된다
  - [ ] Given CLI에서 인증된 상태일 때 When 프로젝트 생성 명령을 실행하면 Then 프로젝트가 생성되고 결과가 표시된다

#### [Agent 프로세스 감지] Task 5.2

### [지휘 채널] Activity 6 — Phase 1

#### [대화] Task 6.1

**FR-026 대화 채널**
- **스토리**: 대표로서 Main·Agent와 대화 채널로 소통하여 지시하고 보고받는다
- **분류**: FR / **우선순위**: Must / **Phase**: 1 / **근거**: D-09
- 수용 기준
  - [ ] Given 시스템이 최초 기동될 때 When 초기화가 완료되면 Then CH-MAIN 채널 1개가 자동 생성되고 삭제할 수 없다
  - [ ] Given Agent가 생성될 때 When 등록이 완료되면 Then 해당 Agent의 CH-AGENT 채널이 자동 생성된다
  - [ ] Given Agent가 종료(completed/cancelled)될 때 When 상태가 변경되면 Then 채널이 읽기 전용으로 전환되고 삭제되지 않는다
  - [ ] Given Sub-Agent가 있을 때 When 대표가 조회하면 Then Sub-Agent와의 직접 대화 채널은 제공되지 않는다 (그래프 규칙 3)

**FR-027 메시지 저장·조회·검색**
- **스토리**: 대표로서 지난 대화가 저장되고 언제든 찾아볼 수 있다
- **분류**: FR / **우선순위**: Must / **Phase**: 1 / **근거**: D-09, D-27
- 수용 기준
  - [ ] Given 대화가 오간 후 When 서버를 재시작하면 Then 모든 메시지가 그대로 조회된다
  - [ ] Given **Agent가 삭제될 때** When 삭제가 완료되면 Then 대화는 삭제되지 않고 `archived`로 전환되며 Agent명·프로젝트명이 보존된다
  - [ ] Given 검색어를 입력할 때 When 전 채널 검색을 실행하면 Then 본문이 일치하는 메시지가 채널명·시각과 함께 반환된다
  - [ ] Given Agent 보고가 도착할 때 When 저장되면 Then 요약·수행 내용·산출물·미해결 사항 4개 필드로 구조화되어 저장된다

**FR-028 의사결정 요청·응답**
- **스토리**: 대표로서 Agent의 의사결정 요청을 등급에 따라 받고 승인·반려한다
- **분류**: FR / **우선순위**: Must / **Phase**: 1 / **근거**: D-10, D-11, D-13
- 수용 기준
  - [ ] Given 등급 '높음' 요청이 발행될 때 When 대표가 응답하기 전이면 Then 해당 Agent는 `waiting` 상태로 대기하고 타임아웃되지 않는다
  - [ ] Given 등급 '보통' 요청이 발행될 때 When 30분이 경과하면 Then 자동 진행되고 그 사실이 시스템 이벤트로 기록된다
  - [ ] Given 등급 '낮음' 결정이 발생할 때 When 처리되면 Then 대화에 노출되지 않고 상태 변경 이력에만 기록된다
  - [ ] Given 대표가 반려할 때 When 사유를 입력하지 않으면 Then 반려가 거부된다

#### [진행 관리] Task 6.2

**FR-029 Phase 진행 추적**
- **스토리**: 대표로서 현재 Phase가 어느 단계에 있고 무엇이 남았는지 한눈에 확인한다
- **분류**: FR / **우선순위**: Must / **Phase**: 1 / **근거**: D-16
- 수용 기준
  - [ ] Given Phase가 진행 중일 때 When 진행 현황을 조회하면 Then 7개 단계(plan~operate)별 상태·산출물 건수·승인 대기 건수가 반환된다
  - [ ] Given 앞 단계가 완료되지 않았는데 다음 단계가 진행 중일 때 When 진행 현황을 조회하면 Then WIP 위반이 근거 수치와 함께 표시된다
  - [ ] Given WIP 위반을 무시하기로 할 때 When 사유와 함께 등록하면 Then 해당 Phase 동안 다시 표시되지 않는다

**FR-030 스킬 전환 승인 게이트**
- **스토리**: 대표로서 `plan→analyze`, `test→deploy` 지점에서 반드시 승인을 거쳐 다음 단계로 넘어간다
- **분류**: FR / **우선순위**: Must / **Phase**: 1 / **근거**: D-14, D-17
- 수용 기준
  - [ ] Given 게이트 지점에 도달할 때 When 다음 단계 착수를 요청하면 Then 승인 없이는 차단되고 승인 요청이 생성된다
  - [ ] Given 게이트 승인 요청이 생성될 때 When 대표가 조회하면 Then **직전 단계 산출물 전체**가 검토 대상으로 함께 제시된다
  - [ ] Given 게이트 승인 요청이 대기 중일 때 When 시간이 경과해도 Then 자동 진행되지 않는다 (타임아웃 없음)
  - [ ] Given 대표가 승인할 때 When 검토 체크리스트를 모두 완료하지 않았으면 Then 승인 버튼이 활성화되지 않는다
  - [ ] Given 게이트를 우회해야 할 때 When 예외 승인을 요청하면 Then 사유와 함께 기록되고 진행이 허용된다

**FR-031 산출물 동기화 추적**
- **스토리**: 대표로서 각 산출물이 Notion과 Git 양쪽에 있는지 확인하여 누락을 발견한다
- **분류**: FR / **우선순위**: Should / **Phase**: 1 / **근거**: D-16
- 수용 기준
  - [ ] Given 산출물 목록을 조회할 때 When 각 산출물에 대해 Then Notion URL과 Git 경로의 존재 여부가 표시된다
  - [ ] Given 한쪽에만 존재하는 산출물이 있을 때 When 목록을 조회하면 Then 미동기화 항목으로 구분 표시된다

#### [실시간 배선] Task 8.2 — WS-01 해소

**INT-004 WebSocket 엔드포인트 배선**

- **분류**: INT / **우선순위**: Must / **복잡도**: **L** / **Phase**: 2A / **근거**: 결함 WS-01

**FR-036 상태·메시지 이벤트 발행**
- **스토리**: 대표로서 CLI나 Agent가 바꾼 상태와 새 메시지가 웹 화면에 바로 반영되는 것을 본다
- **분류**: FR / **우선순위**: Must / **복잡도**: **L** / **Phase**: 2A / **근거**: 결함 WS-01 · DES-007 §9
- 수용 기준
  - [ ] Given 프로젝트·Agent·Task의 상태가 바뀔 때 When 상태 변경이 기록되면 Then `status:changed` 전역 이벤트가 발행된다
  - [ ] Given 상태 변경이 **캐스케이드로** 발생할 때 When 하위 엔티티까지 전이되면 Then 전이된 엔티티마다 이벤트가 발행된다 — 직접 상태 변경과 캐스케이드가 **경로에 무관하게 같은 결과**를 낸다
  - [ ] Given 새 메시지가 저장될 때 When 저장이 완료되면 Then 해당 대화 채널로 `message:new`가 발행된다
  - [ ] Given 이벤트 발행이 실패할 때 When 예외가 발생하면 Then 상태 변경·메시지 저장 트랜잭션은 롤백되지 않는다 (알림 실패가 데이터를 되돌리지 않는다)
  - [ ] Given 구독자가 없을 때 When 발행하면 Then 오류 없이 무시된다

> **왜 별도 스토리인가**: INT-004는 *전송로*, FR-036은 *발신원*이다. 현재 상태 변경 경로에는 broadcast 호출이 **0건**이고, `StatusChangeService`·`ConversationService`는 생성자에 Hub를 주입받지도 않는다. 즉 라우트를 열어도 상태·메시지 이벤트는 저절로 생기지 않는다.

  - [ ] Given 채널을 열 때 When 메시지가 로드되면 Then 최신부터 커서 방식으로 이어 읽을 수 있다

  - [ ] Given 메시지를 보낼 때 When 전송하면 Then 본문만 서버로 보내고 발신자·메시지 유형은 서버가 정한다
  - [ ] Given 종료·보관된 Agent의 채널일 때 When 채널을 열면 Then 읽기 전용으로 표시되고 입력창이 비활성화된다

## INVEST 검증 메모

모든 스토리가 INVEST 기준을 통과한다.

- **Independent**: 각 스토리는 독립 구현 가능 (의존 순서는 있으나 독립 배포 가능)
- **Negotiable**: 구현 방법이 열려 있음 (프레임워크 미결정 상태)
- **Valuable**: 각 스토리가 시스템 기능에 직접 기여
- **Estimable**: 범위가 명확하여 규모 판단 가능
- **Small**: Phase 1 내 완료 가능한 크기
- **Testable**: 모든 Must 스토리에 Given-When-Then 수용 기준 포함

### Phase 2A 스토리 INVEST 검증 (v4.0)

신규 14건 전건 통과. 근거는 아래와 같다.

| 기준 | 판정 근거 |
|------|----------|
| **I**ndependent | 프론트 스토리는 확정된 API 계약을 소비만 하므로 상호 독립이다. 순서 의존(셸 → 화면)은 있으나 병합이 필요한 결합은 없다 |
| **N**egotiable | 구현 방법을 수용 기준에 넣지 않았다. 예외는 FR-034의 "동일 오리진"과 NFR-004의 URI 형식 검증 두 가지이며, 둘 다 접근법 선택·결함 조치로 **의도적으로 고정**한 것이다 |
| **V**aluable | 전건을 "대표가 화면에서 얻는 것"으로 서술했다. INT-004·FR-036 같은 배선 성격 항목도 "새로고침 없이 변화를 본다"는 가치로 환원된다 |
| **E**stimable | 기존 REST 34종 계약이 확정되어 있어 프론트 규모 판단이 가능하다. 유일한 불확실은 INT-004 → **SPIKE-2A-01**로 분리 |
| **S**mall | 최대 복잡도 L 3건(INT-004·FR-036·UIR-010), 전부 Phase 2A 내 완료 가능한 크기 |
| **T**estable | Must 12건 전건이 Given-When-Then을 보유한다 |

**Spike 필요 항목 (Phase 2A)**: **SPIKE-2A-01** — WebSocket 플러그인 + 쿼리 파라미터 토큰 인증 + 기존 `WebSocketHub`(라이브러리 비의존 `HubSocket` 인터페이스) 어댑터의 3자 결합. INT-004 착수 전에 수행한다.
