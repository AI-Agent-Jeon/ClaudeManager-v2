## 역할

| 용어 | 정의 | 비고 |
|------|------|------|
| 대표 (CEO) | 시스템의 유일한 사용자. 모든 의사결정의 최종 권한자 | 1인 CEO |
| Main | 디스패처 에이전트. 요구사항을 수신하고 정형화하며 적절한 스킬을 선택하여 Agent를 생성·위임한다 | Claude Opus |
| Agent | 프로젝트 실행 책임자. Sub-Agent를 관리하고 대표에게 직접 보고한다 | Claude Opus |
| Sub-Agent | 단계별 작업 수행자. Agent에게만 보고한다 | dev-sub, test-sub, review-sub, docs-sub |

## 시스템 개념

| 용어 | 정의 | 비고 |
|------|------|------|
| 프로젝트 | 관리의 최상위 단위. 하나의 목표를 달성하기 위한 작업 묶음 | 상태: 준비→진행 중→완료 등 |
| 스킬 | SDLC 단계별 수행 절차를 정의한 문서. plan, analyze, design, develop, test, deploy, operate | 7개 |
| Phase | 반복 개발의 한 사이클. 기획→운영을 한 바퀴 돈다 | Phase 1: 기반 구축 |
| Walking Skeleton | 모든 주요 기능 영역을 관통하는 최소 동작 흐름 | Phase의 Must 범위 |
| Task | Agent에게 할당된 개별 작업 단위 | 상태: 대기→진행 중→완료 등 |

## 상태 모델

| 용어 | 정의 | 적용 대상 |
|------|------|----------|
| 생성됨 (Created) | 초기 생성 상태 | Agent |
| 준비 (Ready) | 실행 대기 상태 | 프로젝트, Task |
| 실행 중 (Running) | 작업 수행 중 | Agent, 프로젝트 |

| 대기 중 (Waiting) | 외부 입력/승인 대기 | Agent, 프로젝트 |
| 일시정지 (Paused) | 사용자가 중단 | Agent, 프로젝트, Task |
| 완료 대기 (Pending Completion) | 완료 승인 대기 | Agent, 프로젝트 |
| 완료 (Completed) | 정상 종료 | Agent, 프로젝트, Task |
| 실패 (Failed) | 비정상 종료 | Agent, 프로젝트, Task |
| 취소됨 (Cancelled) | 사용자가 취소 | Agent, 프로젝트, Task |

| 검토 중 (In Review) | 결과 검토 중 | Task |

## 기술 용어

| 용어 | 정의 | 비고 |
|------|------|------|
| 백엔드 | 로컬에서 실행되는 HTTP 서버. 웹 UI와 CLI의 통신 중심 | 프레임워크 미결정 |
| SQLite | 파일 기반 관계형 데이터베이스. 1인 사용자 로컬 환경에 적합 | 확정 |
| REST API | HTTP 기반 CRUD 인터페이스 | 확정 |
| WebSocket | 실시간 양방향 통신 프로토콜 | Hub는 **Phase 1**에 구현됐고 엔드포인트 배선은 **Phase 2A**(INT-004 · 결함 WS-01) |
| 마이그레이션 | DB 스키마 변경을 버전 관리하는 체계 | 순방향 실행, 실패 시 롤백 |
| CLI | Command Line Interface. 터미널에서 시스템과 상호작용 | Phase 1 주요 인터페이스 |
| PWA | Progressive Web App. 모바일 브라우저에서 네이티브 앱처럼 동작하는 웹 앱 | **Phase 2B** 반응형 모바일 웹 (D-23) |
| 칸반 (Kanban) | 작업 카드를 컬럼(상태) 간 이동시켜 진행 현황을 시각화하는 관리 기법 | **Phase 2B** (FR-017 · UIR-002) |
| DAG | Directed Acyclic Graph. 순환 없는 방향 그래프. Agent → Sub-Agent 관계 시각화 | Phase 4 오케스트레이션 뷰 |
| 승인 게이트 (Approval Gate) | 특정 단계에서 대표의 명시적 승인을 요구하는 관문 | **Phase 1** 구현 완료 (D-16 · FR-030) |
| 공유 메모리 (Shared Memory) | Agent 간 컨텍스트를 공유하는 저장소. 단기(세션) / 장기(프로젝트) | Phase 3 |
| 워크플로우 템플릿 | Agent/Task 구성을 저장하여 새 프로젝트에서 재사용하는 패턴 | Phase 3 |
| 웹훅 (Webhook) | 이벤트 발생 시 외부 URL로 HTTP POST를 전송하는 알림 방식 | Phase 4 |
| 체크포인트 (Checkpoint) | Agent 작업 시점의 git 스냅샷. 롤백 시 복원 기준점 | Phase 5 |
| 토큰 (Token, LLM) | LLM API 호출 단위. input/output/cached로 분류, 비용 산정 기준 | **Phase 3** 비용 추적 후보 |

## 대화·승인 (Phase 1 도입)

| 용어 | 정의 | 출처 |
|------|------|------|
| 채널 (CH-MAIN / CH-AGENT) | 대표와 Main/Agent 사이의 대화 통로. CH-MAIN은 전역 단일이며 삭제할 수 없고, CH-AGENT는 Agent당 1개 자동 생성된다. Sub-Agent와의 직접 채널은 없다 | DES-013 §2 |
| APV-GATE | 스킬 전환 승인 게이트. `plan→analyze` · `test→deploy` 2곳. **등급 높음 고정, 타임아웃 없음**, Phase 전체를 블로킹한다 | DES-014 §3 |
| WIP 위반 | 앞 단계가 끝나지 않았는데 다음 단계가 진행된 상태. 저장하지 않고 조회 시점에 계산한다 | DES-014 §1-3 |
| 아카이브 (archived) | Agent가 삭제돼도 대화는 지우지 않고 전환하는 상태. Agent명·프로젝트명 스냅샷을 보존한다 | DES-013 §2 (D-27) |

## 웹 UI (Phase 2A 도입)

| 용어 | 정의 | 출처 |
|------|------|------|
| **Phase 2A / 2B** | Phase 2의 분할 단위. **2A = 로컬(`127.0.0.1`) 웹 지휘소**, **2B = 원격·모바일**. 분할해도 최종 범위는 같다 | SCOPE-01 (2026-09-03) |
| 3-Pane | 트리 / 목록 / 상세 3분할 레이아웃. 드릴다운 대신 세 계층을 동시에 보여준다 | DES-012 §6-2 |
| App Shell | 전 인증 화면에 공통으로 깔리는 껍데기 — 상태바(주메뉴·연결 배지·테마 토글) + 사이드바 + 토스트 스택 | DES-012 §5-1 · UIR-009 |
| 워크스페이스 (SCR-W-WS) | 3-Pane 핵심 화면. 프로젝트·Agent·Task를 화면 이동 없이 훑는다 | DES-012 §6-2 · UIR-010 |
| 개요 (SCR-W-OV) | 관제탑 화면. **〈내 결정이 필요합니다〉가 최상단**, 집계는 그 아래 | DES-012 §6-1 · UIR-001 |
| 진행 보드 (SCR-W-PH) | Phase × SDLC 7단계 보드. 게이트 위치와 WIP 위반을 시각화한다 | DES-014 §4 · UIR-012 |
| 승인함 (SCR-W-AP) | 승인의 **작업 공간**. 목록 + 검토 패널 분할. 개요의 결정 카드가 '알림'이라면 승인함은 '결재함'이다 | DES-014 §5 · UIR-005 |
| 커맨드 팔레트 (CMD-01) | `⌘K`로 여는 전역 검색·이동·명령 창 | DES-012 §6-4 — **Phase 2B** |
| **동일 오리진 (Same-Origin)** | 웹 클라이언트와 API를 같은 호스트·포트에서 내보내는 배치. CORS 설정이 불필요해진다 | 접근법 A (PLN-002 Phase 2A) |
| **SPA history fallback** | 클라이언트 경로(`/w` 등)로 직접 접속·새로고침해도 404가 아니라 웹 앱을 돌려주는 서버 규칙 | FR-034 |
| **Walking Skeleton (2A)** | 브라우저 접속 → 로그인 → 상태 확인 → 대화 1왕복 → 승인 1건 → 실시간 갱신 | PLN-002 Phase 2A |
| **고통 목록** | 대표가 2A를 실제로 써보고 기록하는 불편 목록. **2A의 진짜 산출물이자 2B 범위의 입력** | PLN-002 Phase 2A 완료 조건 9 |
| VAPID | Web Push 서버 인증 방식. 키 쌍으로 푸시 발송 권한을 증명한다 | DES-015 §3 — **Phase 2B** |
| WebAuthn | 브라우저 표준 생체인증 API. Face ID·지문으로 승인을 재확인한다. **도메인이 바뀌면 등록한 passkey가 무효**가 된다 | DES-015 §6-4 — **Phase 2B** |
| 터널링 (Tunneling) | 로컬 서버를 고정 도메인으로 외부에 노출하는 방식. **Cloudflare Tunnel 채택**(ADR-010) | ADR-010 — **Phase 2B** |
