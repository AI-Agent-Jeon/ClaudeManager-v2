## Walking Skeleton 재정의 (v2)

**대화와 승인이 Phase 1에 들어왔으므로 최소 동작 흐름도 바뀐다.** v1의 "상태를 조회·변경하는 경로"에 **"지시하고 승인하는 경로"**가 추가된다.

```
서버 기동    인증       프로젝트 생성   Agent 등록    상태 로그
(FR-001) → (FR-002) → (FR-003)    → (FR-007)  → (FR-009)
                                                    ↓
                          ┌─────────────────────────┘
                          ↓
     대화 1왕복      의사결정 1건 승인     CLI 조회
     (FR-026/027) → (FR-028/030)     → (INT-001/003)
        ↓                 ↓                  ↓
    Activity 6        Activity 6         Activity 5
     지휘 채널          승인 게이트          CLI 연동
```

**이 경로가 동작하면 "대표가 지시하고 → 보고받고 → 승인해서 → 다음 단계로 넘어간다"가 성립한다.**
v1 skeleton은 여기서 상태 조회·변경까지만 했다.

### (B) 채택에 따른 리스크 대응

(B)의 단점은 **첫 동작 확인까지 오래 걸린다**는 것이다. 분할 대신 아래로 완화한다.

| 대응 | 내용 |
|------|------|
| **Layer 순서 유지** | Layer 1~6 순서는 그대로 지킨다. Layer 4까지 끝나면 **분할했을 때의 1-A와 동일한 상태**이므로, 그 시점에 중간 점검을 한다 |

## 다중 관점 검토 결과

### CEO 관점 (제품 가치)

- Phase 1 끝나면 사용 가능한 것: CLI에서 프로젝트 생성/조회, Agent 상태 등록/확인, 상태 이력 조회
- Walking Skeleton은 최소 가치: 현재 수동 터미널 관리 → CLI 기반 중앙 관리로 첫 전환
- Won't 중 실은 Must: WebSocket은 Phase 2로 적절 (기반 없이 실시간은 무의미)
- 10점 제품 방향: 기반 인프라 없이는 대시보드/채팅/승인 모두 불가 → 필수 단계

### 기술 관점 (실현 가능성)

- 숨겨진 복잡성: Agent 프로세스 감지 (OS 레벨 모니터링) → Should로 분류, spike 필요
- 순환 의존: 없음 (Layer 1→5 선형 구조)
- 기존 시스템 충돌: 없음 (신규 프로젝트)
- Spike 필요: Agent 프로세스 감지 방식 (polling vs 이벤트 vs Claude Code hooks)

### UX 관점 (사용자 경험)

- Phase 1은 CLI + API 전용 → 웹 UI는 Phase 2
- 에러 시 사용자 경험: CLI 에러 메시지 명확히 (수용 기준에 포함)
- Walking Skeleton만으로 자연스러운 흐름: 서버 시작→로그인→프로젝트 생성→Agent 등록→상태 확인 OK

### 반영 사항

- Agent 프로세스 감지를 Should로 격하 (기술 복잡성)
- CLI 에러 메시지를 수용 기준에 명시 (UX)
