## 문제 검증 결과 요약

- **수요 현실**: 에이전트마다 별도 터미널 관리 → 동시 감독 불가, 상태 누락 (5가지 구체적 고통 확인)
- **현재 대안**: 터미널 수동 전환, 스크롤백 의존 → 영속성 없음, 프로젝트별 비용 구분 불가
- **최소 범위**: Phase 1은 7개 항목(백엔드, CLI, 인증, 프로젝트, 상태, 로그, 감지)으로 한정
- **전제 리스크**: SQLite 단일 사용자 충분, 로컬 실행 전제 → 틀려도 마이그레이션 체계로 대응 가능

## Walking Skeleton 재정의 (v2)

**대화와 승인이 Phase 1에 들어왔으므로 최소 동작 흐름도 바뀐다.** v1의 "상태를 조회·변경하는 경로"에 **"지시하고 승인하는 경로"**가 추가된다.

```
서버 기동    인증       프로젝트 생성   Agent 등록    상태 로그
(FR-001) → (FR-002) → (FR-003)    → (FR-007)  → (FR-009)
                                                    ↓
                          ┌─────────────────────────┘
                          ↓
     대화 1왕복      의사결정 1건 승인     CLI 조회
     (FR-026/027) → (FR-028/030)     → (INT-001/003)
        ↓                 ↓                  ↓
    Activity 6        Activity 6         Activity 5
     지휘 채널          승인 게이트          CLI 연동
```

**이 경로가 동작하면 "대표가 지시하고 → 보고받고 → 승인해서 → 다음 단계로 넘어간다"가 성립한다.**
v1 skeleton은 여기서 상태 조회·변경까지만 했다.

## ⚠ 범위 분할 제안 — 대표 결정 필요 (D-30)

Must가 12 → 19개, 복잡도 L이 2 → 6개로 늘었다. **한 번에 다 끝내려 하면 Walking Skeleton의 이점(빠른 동작 확인)이 사라진다.**

### 선택지

| 안 | 구성 | 장점 | 단점 |
|---|------|------|------|
| **(A) Phase 1 분할** ← 권고 | **1-A**: Layer 1~4 + CLI 기본 (기존 12개)<br>**1-B**: Layer 5~6 대화·승인 (신규 7개) | 1-A가 끝나면 **동작하는 것이 손에 잡힌다.** 1-B는 그 위에 얹는다. 리스크 조기 발견 | Phase 하나가 둘로 늘어 관리 단위 증가 |
| (B) 통합 진행 | 19개를 한 Phase로 | 관리 단위 단순 | **첫 동작 확인까지 오래 걸린다.** RISK-006(복잡도 과소평가)이 커짐 |
| (C) 일부 Phase 2로 환원 | 대화·승인 중 일부를 Phase 2로 | 범위 축소 | **D-09·D-16 승인을 뒤집는 것** — 제품 가설 검증이 다시 미뤄짐 |

### 권고: (A) Phase 1 분할

| 단계 | 범위 | 완료 시 가능한 것 |
|------|------|-----------------|
| **Phase 1-A** | Layer 1~4 (FR-001~009, DAT-001/002, NFR-002, INT-001) | CLI로 프로젝트·Agent·Task를 만들고 상태를 추적한다 |
| **Phase 1-B** | Layer 5~6 (FR-026~030, DAT-003, INT-003) | **Main·Agent와 대화하고 승인 게이트로 진행을 통제한다** |

**근거**: 1-A는 v1 계획 그대로라 검증된 순서다. 1-B의 신규 7건 중 4건이 복잡도 L이라, 1-A가 동작하는 걸 확인한 뒤 얹는 편이 안전하다. 분할해도 **최종 Phase 1 범위는 그대로**이므로 D-09·D-16 승인을 뒤집지 않는다.

> 이 결정은 `docs/00-approvals.md`에 **D-30**으로 등록되어 있다.

## 다중 관점 검토 결과

### CEO 관점 (제품 가치)

- Phase 1 끝나면 사용 가능한 것: CLI에서 프로젝트 생성/조회, Agent 상태 등록/확인, 상태 이력 조회
- Walking Skeleton은 최소 가치: 현재 수동 터미널 관리 → CLI 기반 중앙 관리로 첫 전환
- Won't 중 실은 Must: WebSocket은 Phase 2로 적절 (기반 없이 실시간은 무의미)
- 10점 제품 방향: 기반 인프라 없이는 대시보드/채팅/승인 모두 불가 → 필수 단계

### 기술 관점 (실현 가능성)

- 숨겨진 복잡성: Agent 프로세스 감지 (OS 레벨 모니터링) → Should로 분류, spike 필요
- 순환 의존: 없음 (Layer 1→5 선형 구조)
- 기존 시스템 충돌: 없음 (신규 프로젝트)
- Spike 필요: Agent 프로세스 감지 방식 (polling vs 이벤트 vs Claude Code hooks)

### UX 관점 (사용자 경험)

- Phase 1은 CLI + API 전용 → 웹 UI는 Phase 2
- 에러 시 사용자 경험: CLI 에러 메시지 명확히 (수용 기준에 포함)
- Walking Skeleton만으로 자연스러운 흐름: 서버 시작→로그인→프로젝트 생성→Agent 등록→상태 확인 OK

### 반영 사항

- Agent 프로세스 감지를 Should로 격하 (기술 복잡성)
- CLI 에러 메시지를 수용 기준에 명시 (UX)

### 미해결

- 프레임워크 선택 → analyze 단계에서 ADR로 결정
- Agent 프로세스 감지 방식 → analyze 단계에서 spike
- 인증 토큰 방식 상세 (JWT vs 단순 토큰) → design 단계에서 결정
