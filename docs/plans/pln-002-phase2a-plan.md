## Phase 목표

**브라우저에서 대표가 상태를 훑고, 대화하고, 승인할 수 있게 만든다. 그리고 그것을 실제로 써서 진짜 고통을 발견한다.**

이 Phase의 산출물은 화면 5개가 아니라 **실사용 고통 목록**이다.

---

## ⚠ 이 Phase의 성격 — 먼저 읽어야 할 전제

강제 질문 **'수요 현실'**에 대한 대표의 답변은 *"아직 CLI를 써보지 않았다"*였다.
즉 **Phase 1의 34개 CLI 화면이 실제로 어떤 고통을 남기는지에 대한 데이터가 없다.**

Phase 1에서 이미 같은 값을 치렀다. 아래 세 결함은 전부 **"만들었지만 써보지 않아서"** 생긴 것이다.

| 결함 | 내용 |
|------|------|
| DES-006 `--stage` / `--skill` | 문서대로 명령을 치면 실패했다 |
| NEW-04 `.env` 미로딩 | 안내대로 `.env`를 만들어도 무시되고 토큰이 매번 무효화됐다 |
| NEW-01 `db:migrate` 무동작 | "마이그레이션 완료"로 오판할 수 있었다 |

따라서 Phase 2A의 모든 판단 기준은 다음 한 줄이다.

> **추측으로 화면을 정교하게 만들지 않는다. 빨리 띄워서, 실제로 쓰고, 진짜 고통을 기록한다.**

DES-011·DES-012·DES-013·DES-014의 웹 설계는 이미 존재하지만 **CLI를 써본 적 없는 상태에서 그린 것**이다. 맹신하지 않고 2A 범위에 맞게 잘라 쓴다.

## 선택한 접근법 (3단계)

> **전제**: 프론트 스택은 이미 ADR로 확정되어 있다 — **ADR-002** React + Vite, **ADR-006** Tailwind CSS, **ADR-007** shadcn/ui + cmdk + TanStack Table.
> 3단계는 스택 재논의가 아니라 **2A에서 그것을 어떻게 배치할 것인가**를 정한다.

### 접근법 A: 동일 오리진 SPA — 빌드 산출물을 백엔드가 서빙 ★ **추천·채택**

- **핵심**: `src/frontend`를 4번째 npm workspace로 신설. 개발 중에만 Vite 개발 서버를 쓰고 `/api`·`/ws`를 백엔드로 프록시한다. 실행은 빌드 산출물을 Fastify 정적 서빙 + SPA history fallback으로 내보낸다
- **범위**: 2A 화면 전부
- **장점**
  - ADR-002·006·007과 **전건 정합** — 대표 승인(D-03·D-04)을 뒤집지 않는다
  - **동일 오리진이라 CORS 플러그인이 필요 없다.** 현재 `@fastify/cors`는 설치돼 있지 않다
  - 토큰과 WebSocket 쿼리 인증이 한 오리진에 묶여 인증 모델이 단순하다
  - 2B 터널링 시 외부에 노출할 포트가 **1개**로 유지된다
- **리스크**: 개발(프록시)과 실행(정적)의 두 경로가 갈린다. **Phase 1의 `.env` 미로딩·`db:migrate` 무동작과 같은 계열** — 선언된 절차가 실제로는 돌지 않는 자리다. 또 `app.ts:123`의 `setNotFoundHandler`가 모든 non-API 경로를 404 JSON으로 응답하므로 SPA fallback과 등록 순서가 충돌한다
- **완화**: Phase 완료 조건에 **"빌드 후 백엔드 단일 프로세스만 기동해 실사용"**을 명문화한다. 개발 프록시로만 확인하고 끝내지 않는다
- **예상 규모**: Must 12 · Should 3 · Could 1, 복잡도 L 3건

### 접근법 B: 빌드 없는 정적 HTML + ESM (번들러 없음) — 기각

- **핵심**: 순수 HTML/JS를 정적 서빙만으로 내보낸다. 빌드 단계 0
- **장점**: 가장 빨리 뜬다. `npm run build` 미구성(NEW-06)에 걸리지 않는다
- **기각 사유**: Tailwind · shadcn/ui · TanStack Table을 전부 쓸 수 없다 → **ADR-006·ADR-007 폐기이며 대표 승인 D-03·D-04를 뒤집는다.** 2B에서 전면 재작성해야 하므로 2A에서 아낀 시간을 초과해 잃는다

### 접근법 C: SSR 프레임워크(Next.js / Remix) 도입 — 기각

- **기각 사유**: Fastify 백엔드와 REST 34종이 이미 확정되어 있다. SSR 서버를 하나 더 띄우면 **프로세스 2개 · 인증 2중화**가 된다. 1인 로컬 루프백 앱에 SEO·초기 렌더 이점이 없고 ADR-002를 재개정해야 한다

### 추천 및 부속 결정

| 항목 | 결정 | 등급 | 근거 |
|------|------|:---:|------|
| **구현 배치** | **접근법 A** | 높음 | 위 |

## 백엔드 신규 개발 최소화 — 판정 결과

> **2A 전제: 기존 API를 그대로 쓴다.** 새 엔드포인트가 필요하다고 판단되면 왜 기존 API로 안 되는지를 근거와 함께 남긴다.

**신규 REST 엔드포인트: 0종. 신규 DB 테이블: 0개.**

| 2A 화면 | 사용하는 기존 API | 충분한가 |
|---------|------------------|:---:|
| 로그인 | `POST /api/auth/login` | ✅ |
| 워크스페이스 3-Pane | `GET /api/projects` · `/agents` · `/tasks` · `/status-changes` (+ 각 상세) | ✅ |
| 진행 보드 | `GET /api/phases/current` **단독** — 7단계·게이트·WIP 위반·산출물 건수·승인 대기 건수를 한 번에 준다 | ✅ |
| 승인함 | `GET /api/approvals` · `/approvals/:id` · `POST /api/approvals/:id/resolve` · `GET /api/artifacts` · `/artifacts/:id/content` | ✅ |
| 대화 | `GET /api/conversations` · `/:id/messages` · `POST /:id/messages` · `PATCH /:id/read` · `GET /conversations/search` · `/:id/export` | ✅ |
| 전역 이력 | `GET /api/status-changes` | ✅ |

**추가되는 것 2가지 — 둘 다 API 계약 확장이 아니다.**

| 추가 | 성격 |
|------|------|
| WebSocket 2종 (`/ws`, `/ws/conversations/:id`) | **신규 개발이 아니라 미구현분의 배선이다.** DES-002 §3-2·§3-4에 이미 명세되어 있고 결함 **WS-01**로 등록되어 있다 |
| 정적 서빙 라우트 (SPA fallback + 자산 경로) | API가 아니라 클라이언트 전달 경로 |

### 포기한 화면과 사유

| 화면 | 사유 |
|------|------|
| **UIR-003 Agent Board (실시간 로그)** | DES-012 §6-3이 요구하는 `WS /ws/agents/:id/logs`가 **API 34종에 존재하지 않는다.** 새 백엔드 엔드포인트가 필요하므로 "기존 API를 그대로 쓴다"는 2A 전제와 충돌한다 → 2B |
| **CMD-01 커맨드 팔레트** | 2A는 화면이 4개뿐이라 도달 깊이가 얕다. DES-012가 팔레트로 해소하려던 U-5(깊은 드릴다운)가 2A에는 존재하지 않는다 → 2B |

## Walking Skeleton (7단계)

```
FR-034 서빙 → FR-035 로그인 → UIR-009 셸 → UIR-010 워크스페이스(읽기)
   → INT-004 WS 배선 → FR-037+UIR-011 대화 1왕복
   → FR-038+UIR-005 승인 1건 처리 → FR-036 상태 이벤트 발행
```

**한 줄로**: 브라우저로 접속해 로그인하고, Agent 상태를 훑고, 대화를 1왕복 하고, 승인을 1건 처리하고, **CLI에서 상태를 바꾸면 새로고침 없이 화면이 갱신된다.**

### 🔵 중간 점검 지점 (W2 완료) — 필수

**대표가 브라우저로 직접 로그인해 워크스페이스·진행 보드를 훑고, 그 자리에서 겪은 고통을 목록으로 기록한다.**

- ⚠ **범위 안내**: 이 시점은 **읽기만 가능**하다. 대화·승인은 아직 없다. 안내 없이 시연하면 "기능이 없다"는 오해가 생긴다

## Phase 2A 완료 조건

1. Walking Skeleton 전체 동작: 브라우저 접속 → 로그인 → 워크스페이스에서 상태 확인 → **대화 1왕복 → 승인 1건 처리 → CLI에서 상태 변경 시 새로고침 없이 화면 갱신**
2. Must 스토리 **12개** 전건 구현 및 단위 테스트 통과
3. **`/ws` · `/ws/conversations/:id` 두 엔드포인트가 실제로 연결을 수락**하고, 인증 실패 시 4001 · 대상 없음 시 4004로 종료된다 (결함 WS-01 해소)
4. **상태 캐스케이드 경로에서 `status:changed`가 발행**된다 — 직접 상태 변경과 캐스케이드가 경로 무관하게 같은 결과를 낸다
5. **결함 R2-06 해소** — `notionUrl` URI 형식 검증이 동작하고, 비-HTTP 스킴이 링크로 활성화되지 않는다
6. 검색 조각·메시지 본문·산출물 본문 렌더에서 **스크립트가 실행되지 않는다** (NFR-004)
7. **프론트를 빌드한 뒤 백엔드 단일 프로세스만 기동해** 전 기능이 동작한다 — 개발 프록시 의존이 없다
8. 신규 REST 엔드포인트 **0종** · 신규 DB 테이블 **0개**가 유지되었다
9. 🔵 **대표가 실사용 세션을 최소 1회 수행하고, 겪은 고통을 목록으로 기록했다** — 이 목록이 Phase 2B 범위의 입력이 된다

> 9번이 이 Phase의 존재 이유다. 1~8이 전부 통과해도 9가 비어 있으면 **Phase 2A는 목적을 달성하지 못한 것이다.**
