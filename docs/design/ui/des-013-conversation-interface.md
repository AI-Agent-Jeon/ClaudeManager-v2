# DES-013 대화 인터페이스 설계서

> 문서코드: DES-013
> 버전: v1 (2026-09-01)
> 범위: 대표 ↔ Main / Agent 대화 채널 · 메시지 체계 · 의사결정 요청 흐름 · CLI/웹 대응
> 레이아웃: DES-012 §6-2, §6-3 참조

> **대표 승인 필요 — 의사결정 등급 "높음"**
> 본 문서는 **신규 기능 영역**을 정의한다. 기존 Phase 1 범위(CLI CRUD walking skeleton)와 Phase 2 범위(웹 대시보드)에 모두 포함되지 않은 요구사항이다.
> §7 파급 영향과 §8 의사결정 요청을 먼저 검토할 것. 특히 **D-09(Phase 배치)**가 결정되어야 후속 설계·개발이 진행된다.

---

## 1. 배경 — 왜 이 문서가 필요한가

CLAUDE.md는 대표가 Main·Agent와 **대화하며** 프로젝트를 수행하는 것을 전제한다. 그러나 현재 설계 산출물 어디에도 그 대화가 일어나는 자리가 없다.

| 문서 | 다루는 것 | 대화 |
|------|----------|------|
| DES-006 화면 명세서 (CLI) | 프로젝트/Agent/Task CRUD 명령 19종 | ❌ 없음 |
| DES-011 화면 명세서 (웹) | 목록·상세·상태변경 화면 10종 | ❌ 없음 |
| DES-012 UI 레이아웃 | 3-Pane 레이아웃, 커맨드 팔레트 | 자리만 확보 (§6-3 탭) |
| DES-002 API 명세서 | 6그룹 16엔드포인트 | ❌ 없음 |
| DES-003 데이터 모델 | projects, agents, tasks, status_changes | ❌ 없음 |

현행 설계대로 구현하면 **상태를 조회하고 바꾸는 도구**는 만들어지지만, **지시하고 보고받는 도구**는 만들어지지 않는다. 대표가 실제로 프로젝트를 수행하려면 후자가 있어야 한다.

## 2. 채널 구조

CLAUDE.md의 그래프 규칙이 채널 구조를 그대로 결정한다.

```
대표 (CEO)
  │
  ├─ CH-MAIN ──────► Main (디스패처)          규칙 1: 생성·위임 후 실무 미개입
  │                    │
  │                    └─ Agent 생성 + CH-AGENT 개설
  │
  └─ CH-AGENT ─────► Agent (프로젝트 실행 책임자)  규칙 2: 대표에게 직접 보고
                       │
                       └─ Sub-Agent            규칙 3: 대표 직접 접근 불가
                            │                          → CH-AGENT에 인용으로만 노출
                            └─ (파일 기반 수평 통신)   규칙 4: .orchestrator/handoff, feedback
```

| 채널 ID | 상대 | 개수 | 목적 | 대표 발화 |
|---------|------|------|------|----------|
| **CH-MAIN** | Main | **1개 (전역 단일)** | 요구사항 접수 → 스킬 탐색·제안 → Agent 생성·위임 | ✅ 가능 |
| **CH-AGENT** | Agent | **Agent당 1개** | 진행 보고, 의사결정 요청, 산출물 전달, 대표 지시 수신 | ✅ 가능 |
| (없음) | Sub-Agent | — | 대화 채널 **없음**. 보고는 CH-AGENT에 MSG-05 인용으로만 노출 | ❌ 규칙 3 |

### 채널 생명주기

| 시점 | 동작 |
|------|------|
| 시스템 최초 기동 | CH-MAIN 1개 자동 생성. 삭제 불가 |
| Agent 생성 | 해당 Agent의 CH-AGENT 자동 생성 |
| Agent 종료(completed/cancelled) | CH-AGENT는 **읽기 전용**으로 전환. 삭제하지 않음 (감사 추적) |
| Agent 삭제 | CH-AGENT와 메시지 CASCADE 삭제. 단 decision_requests 이력은 보존 |

## 3. 메시지 체계

### 3-1. 메시지 유형

| 코드 | 유형 | 발신자 | 내용 | 렌더링 |
|------|------|--------|------|--------|
| **MSG-01** | 대표 발화 | 대표 | 요구사항·지시·의사결정 응답 | 우측 정렬 버블 |
| **MSG-02** | Main 응답 | Main | 스킬 탐색 결과, 제안, 위임 결과 | 좌측 버블 + 스킬 배지 |
| **MSG-03** | Agent 보고 | Agent | **CLAUDE.md 보고 형식 4단** (요약 / 수행 내용 / 산출물 / 미해결 사항) | 좌측 카드 (4개 섹션 접기 가능) |
| **MSG-04** | 의사결정 요청 | Main·Agent | 등급 + 안건 + 선택지 + 기한 | **강조 카드 + 액션 버튼** |
| **MSG-05** | 시스템 이벤트 | 시스템 | 상태 전이, Sub-Agent 완료 인용, 타임아웃 자동진행 기록 | 중앙 정렬 dim 1행 |
| **MSG-06** | 산출물 링크 | Agent | docs/ 경로, Notion URL, PR 링크 | 파일 칩 (아이콘 + 코드/제목) |

### 3-2. MSG-03 Agent 보고 렌더링

CLAUDE.md가 규정한 보고 형식을 그대로 구조화한다. 자유 텍스트가 아니라 **4개 필드로 파싱해 저장**한다.

```
┌─ dev-sub-01 · 11:15 ─────────────────────────────────┐
│ 요약                                                  │
│   인증 API 구현 완료. 단위 테스트 12건 통과.            │
│ ─────────────────────────────────────────────────────│
│ ▾ 수행 내용                                            │
│   POST /api/auth/login 엔드포인트 구현, JWT 발급...    │
│ ─────────────────────────────────────────────────────│
│ ▾ 산출물                                               │
│   📄 src/backend/routes/auth.ts                       │
│   📄 tests/unit/auth.test.ts                          │
│ ─────────────────────────────────────────────────────│
│ ⚠ 미해결 사항                                          │
│   토큰 갱신(refresh) 정책 미정 — 대표 결정 필요        │
└──────────────────────────────────────────────────────┘
```

> 「미해결 사항」에 대표 결정이 필요한 항목이 있으면, Agent는 **MSG-04를 별도로 발행**해야 한다. 보고문 안에 묻어두지 않는다.

### 3-4. 등급별 동작

CLAUDE.md 의사결정 등급표를 그대로 구현한다.

| 등급 | 채널 동작 | 개요 DecisionCard | Agent 상태 | 타임아웃 |
|------|----------|------------------|-----------|---------|
| **높음** | MSG-04 발행 + 응답 전까지 **작업 블록** | 표시 (적색) | `waiting` (사유: 대표 응답 대기) | 없음 — 무기한 대기 |
| **보통** | MSG-04 발행, 작업은 계속 진행 | 표시 (황색) | `running` 유지 | 있음 — 경과 시 자동 진행 + MSG-05 기록 |
| **낮음** | MSG-04 **발행하지 않음** | 없음 | `running` | — |

> **낮음** 등급은 대화에 노출하지 않고 status_changes 이력에만 남긴다. 대표의 주의를 소모하지 않는 것이 등급 체계의 목적이다.

### 3-5. 대표 응답 경로

| 경로 | 동작 |
|------|------|
| 개요 DecisionCard 버튼 | 원클릭 승인/반려 → 해당 CH에 MSG-01 자동 기록 |
| 대화 입력창 자유 서술 | 자연어 응답. Agent가 해석해 진행 |
| 커맨드 팔레트 (`⌘⇧M`) | Main에게 지시 |
| CLI `cm decide <id> --approve` | 비대화형 응답 (§5) |

## 5. CLI 대응 (Phase 1)

Phase 1이 CLI 전용이므로, 대화 기능이 Phase 1에 포함될 경우(D-09) 아래 명령군이 필요하다. DES-006 화면 인벤토리에 **SCR-CH01~05 5개 화면 추가**.

| 화면 ID | 명령어 | 기능 | 인증 |
|---------|--------|------|------|
| SCR-CH01 | `cm chat main` | Main과 대화형 세션 (REPL) | 필요 |
| SCR-CH02 | `cm chat agent <id>` | Agent와 대화형 세션 | 필요 |
| SCR-CH03 | `cm chat send main "<본문>"` | 비대화형 1회 전송 (스크립트·CI용) | 필요 |
| SCR-CH04 | `cm inbox` | 미응답 의사결정 요청 목록 | 필요 |
| SCR-CH05 | `cm decide <id> --approve \| --reject --reason "<사유>"` | 의사결정 응답 | 필요 |

  dq3c4d5e   보통    plan 스킬로 진행         main           8분       22분 남음

## 6. 데이터 모델 · API 제안

> 확정이 아니라 **제안**이다. 승인 시 DES-003·DES-002를 정식 개정한다.

### 6-1. 신규 테이블 3종

| 테이블 | 주요 컬럼 | 비고 |
|--------|----------|------|
| `conversations` | id, channel_type(`main`\|`agent`), entity_id(nullable), status(`active`\|`readonly`), created_at | `main`은 entity_id NULL, 전역 1행 |
| `messages` | id, conversation_id(FK), msg_type(MSG-01~06), sender_role, body, structured(JSON), created_at | MSG-03의 4단 보고는 `structured`에 저장 |
| `decision_requests` | id, message_id(FK), level(`high`\|`medium`\|`low`), subject, options(JSON), deadline_at, resolved_at, resolution, resolved_by | `low`는 발행하지 않으므로 실제로는 high/medium만 적재 |

인덱스: `messages(conversation_id, created_at)`, `decision_requests(resolved_at)` — 미응답 조회용.

### 6-2. 신규 엔드포인트 6종

| 메서드 | 경로 | 기능 |
|--------|------|------|
| GET | `/api/conversations` | 채널 목록 + 미읽음 수 |
| GET | `/api/conversations/:id/messages` | 메시지 조회 (커서 페이지네이션) |
| POST | `/api/conversations/:id/messages` | 대표 발화 전송 |
| GET | `/api/decisions?status=pending` | 미응답 의사결정 요청 |
| POST | `/api/decisions/:id/resolve` | 의사결정 응답 |
| WS | `/ws/conversations/:id` | 메시지 스트리밍 |
