# DES-015 모바일 웹(PWA) 설계서

> 문서코드: DES-015
> 버전: **v2 (2026-09-01)** — 네이티브 앱 → **모바일 웹(PWA)**으로 방향 변경
> 대상: 모바일 브라우저 (iOS Safari / Android Chrome), 홈 화면 추가 시 PWA
> 기능 범위: **알림 + 승인 + 진행 확인** (대표 확정, 변경 없음)
> 연계: DES-012 반응형 전략 / DES-014 진행 보드·승인함의 모바일 뷰

> **대표 승인 필요 — 의사결정 등급 "높음" 3건**
> §8 의사결정 요청 참조. **D-19(접속 방식)**는 여전히 최우선 블로커이며, 모바일 웹으로 바뀌면서 **선택지가 사실상 하나로 좁혀졌다**(§2-2).

## 0. v1(네이티브 앱) 대비 변경점

| 항목 | v1 네이티브 앱 | **v2 모바일 웹(PWA)** |
|------|--------------|---------------------|
| 코드베이스 | React Native 별도 1개 추가 | **웹과 동일한 1개** (브레이크포인트 분기) |
| 배포 | TestFlight / Android 내부 테스트 | **URL 접속만** — 심사·서명·스토어 계정 불필요 |
| Phase 배치 | Phase 3 신설 | **Phase 2에 통합 가능** |
| 화면 정의 | 별도 8화면 (SCR-M-*) | **기존 화면의 모바일 뷰** — 신규 화면 1개뿐 |
| 푸시 | Expo Push Service | **Web Push (VAPID)** |
| 생체인증 | `expo-local-authentication` | WebAuthn / Passkey |
| 개발 비용 | 대 | **소** |
| iOS 푸시 | 안정적 | **홈 화면 추가 필수 · iOS 16.4+** ⚠ |
| 백그라운드 처리 | 자유 | 제한적 (푸시 수신은 정상) |

<!-- 방향 전환의 정당성을 명시 -->
> **판단**: 네이티브 앱의 이점(백그라운드 자유도, 강력한 오프라인)은 "알림 받고 승인한다"는 이 앱의 시나리오에 거의 필요 없다. 반대로 코드베이스 1개·배포 URL 하나라는 이점은 1인 프로젝트에서 결정적이다. **모바일 웹이 이 제품에 맞는 선택이다.**

## 1. 목적과 범위

### 1-1. 왜 모바일이 필요한가 (v1과 동일)

DES-012 D-07은 반응형 범위를 "데스크톱 전용(≥1280px)"으로 권고하며 "모바일은 별도 푸시 알림으로 해결 권장"이라고 적었다. 이제 그 권고를 **뒤집는다** — 같은 웹이 모바일까지 담당한다 (§8 D-25).

| 상황 | 현재 | 도입 후 |
|------|------|--------|
| 대표가 자리에 있음 | 웹 대시보드 (3-Pane) | 동일 |
| 대표가 자리를 비움 | **승인 대기가 무기한 방치** — APV-GATE는 타임아웃도 없다 | 푸시 → 확인 → 승인 |
| Agent 실패 발생 | 돌아올 때까지 모름 | 즉시 푸시 |

> 이 제품의 병목은 **대표의 응답 지연**이다. 등급 '높음'과 APV-GATE는 타임아웃이 없어(DES-013 §3-4, DES-014 §3-2) 대표가 없으면 Phase 전체가 멈춘다. 모바일은 기능 추가가 아니라 **병목 해소**다.

### 1-2. 범위 — 하는 것 / 안 하는 것

| 구분 | 항목 |
|------|------|
| **한다** | 푸시 알림 / 승인 요청 검토·승인·반려 / Phase 진행 확인 / 산출물 읽기 |
| **안 한다** | 프로젝트·Agent·Task 생성·수정 / 3-Pane 워크스페이스 / 로그 스트리밍 |
| **나중에 (저비용)** | Main·Agent 대화 — 채팅 UI는 모바일에 자연스럽고 같은 코드베이스라 추가 비용이 작다. Phase 2 이후 판단 |

> 생성·수정은 데스크톱/CLI에서 한다. 모바일은 **읽고 결정하는** 뷰다. 범위를 좁게 유지하는 것이 이 설계의 핵심 결정이며, v1에서 바뀌지 않았다.

## 2. 선결 문제 — 접속 방식 (여전히 최우선)

### 2-1. 문제

DES-001 아키텍처와 DES-006 SCR-S01은 서버를 이렇게 정의한다.

```
CM_HOST = 127.0.0.1     ← 루프백. 같은 PC에서만 접근 가능
CM_PORT = 3000          ← 평문 HTTP
```

**휴대폰은 `127.0.0.1:3000`에 접근할 수 없다.** 이 제약은 네이티브든 웹이든 동일하다.

### 2-2. 모바일 웹이 되면서 선택지가 좁혀졌다

PWA의 핵심 기능은 전부 **secure context(HTTPS)를 요구**한다.

| 기능 | HTTPS 필요 | HTTP에서 |
|------|:---:|---------|
| Service Worker | ✅ | 등록 불가 |
| Web Push | ✅ | 구독 불가 |
| WebAuthn (생체인증) | ✅ | 사용 불가 |
| 홈 화면 추가 (설치) | ✅ | 불가 |

<table>
</table>

| 방식 | HTTPS | 밖에서 승인 | PWA 동작 | 판정 |
|------|:---:|:---:|:---:|------|
| (A) LAN 바인딩 (`0.0.0.0`, 사설 IP) | ❌ 평문 | ❌ | ❌ **전 기능 불가** | **탈락** |
| **(B) 터널링** (Tailscale / Cloudflare Tunnel) | ✅ 자동 발급 | ✅ | ✅ | **권고** |
| (C) 클라우드 배포 | ✅ | ✅ | ✅ | 가능하나 로컬 MVP 전제가 무너짐 |

> **v1에서는 (A)가 "밖에서는 못 쓰지만 집에서는 된다"는 절충안이었다. v2에서는 HTTPS가 없어 PWA 기능이 전부 죽으므로 완전히 탈락한다.** D-19의 실질 선택지는 (B)와 (C) 둘뿐이고, 로컬 MVP·SQLite·단일 사용자 전제를 지키려면 **(B) 터널링**이다.

### 2-3. 푸시의 외부 의존 (v1과 동일)

Web Push도 결국 Apple/Google 인프라를 경유한다. 우회 방법은 없다.

```
ClaudeManager 서버 ─(VAPID 서명)→ Push Service ─→ 단말
                                   ├ Android: FCM
                                   └ iOS: Apple Web Push
```

CLAUDE.md 의사결정 등급표상 **"외부 API 연동 = 등급 높음"**이므로 승인 대상이다 (APV-EXT). §8 D-21.

| 전송 내용 | 외부로 나가는가 |
|----------|---------------|
| 알림 제목·본문 | ✅ 나감 — **안건 제목이 Apple/Google 서버를 거친다** |
| 산출물 본문·근거 | ❌ 안 나감 — 브라우저가 서버에서 직접 조회 |
| 승인 결과 | ❌ 안 나감 |

> **완화**: 푸시 본문에는 식별자와 최소 문구만 담는다(§5-2). 민감 정보가 외부를 거치지 않는다.
> **v1 대비 개선**: Expo 계정·APNs 인증서·앱스토어 등록이 사라지고 **VAPID 키 쌍 하나만** 서버가 보관하면 된다. 외부 의존 표면이 줄었다.

## 3. 기술 스택 제안

| 항목 | 제안 | 근거 |
|------|------|------|
| 프레임워크 | **웹과 동일** (React + Tailwind + shadcn/ui) | DES-012 D-03과 정합. **새 스택을 도입하지 않는다** |
| 반응형 | Tailwind 브레이크포인트 + 레이아웃 컴포넌트 분기 | §4-1 |
| PWA | `manifest.json` + Service Worker | 홈 화면 추가, 오프라인 캐시, 푸시 수신 |
| 푸시 | **Web Push (VAPID)** — `web-push` 서버 라이브러리 | 인증서·스토어 계정 불필요 |
| 인증 | JWT (웹과 동일) + **QR 페어링** | 폰에서 시크릿 타이핑은 실용적이지 않다 |
| 토큰 저장 | `IndexedDB` (Service Worker 접근 가능) + `httpOnly` 쿠키 병용 검토 | `localStorage`는 XSS에 취약 |
| 생체인증 | **WebAuthn platform authenticator** (Face ID / 지문) | §6-3 |
| 배포 | **없음** — 데스크톱 웹과 같은 서버·같은 URL | 심사·서명·버전관리 불필요 |

## 4. 반응형 전략 ★ 핵심

### 4-1. 브레이크포인트

DES-012의 3-Pane은 데스크톱 전용이다. 폭이 줄면 단계적으로 접힌다.

| 구간 | 폭 | 레이아웃 | 네비게이션 |
|------|-----|---------|-----------|
| **Desktop** | ≥1280px | **3-Pane** (트리 / 목록 / 상세) | 상단 메뉴 6개 |
| **Tablet** | 768 ~ 1279px | **2-Pane** — Pane 1 트리가 드로어로 접힘 | 상단 메뉴 + 햄버거 |
| **Mobile** | <768px | **1-Pane 드릴다운** | **하단 탭 4개** |

```
Desktop (≥1280)          Tablet (768~1279)       Mobile (<768)
┌───┬─────┬─────┐        ┌─────────┬─────┐       ┌───────────┐
│ 1 │  2  │  3  │   →    │    2    │  3  │   →   │   1개씩    │
│트리│ 목록 │ 상세 │        │  목록   │ 상세 │       │  드릴다운  │
└───┴─────┴─────┘        └─────────┴─────┘       ├───────────┤
                          ☰ 트리는 드로어          │ 홈 승인 진행 설정│
                                                 └───────────┘
```

### 4-2. 모바일에서 노출하는 라우트

**URL은 데스크톱과 동일하다.** 같은 주소를 폰에서 열면 모바일 레이아웃으로 렌더링된다.

| 라우트 | 데스크톱 | 모바일 | 탭 |
|--------|---------|--------|-----|
| `/` | 개요 (3열 그리드) | **홈** — 의사결정 카드 세로 스택 | 탭 1 |
| `/approvals` | 승인함 (목록+검토 패널) | **승인 목록** — 검토는 별도 화면 | 탭 2 |
| `/approvals/:id` | 우측 검토 패널 | **승인 상세** — 전체 화면 | — |
| `/progress` | 진행 보드 (가로 칸반) | **진행** — 세로 스텝 | 탭 3 |
| `/settings` | 설정 | **설정** (+ 알림 설정) | 탭 4 |
| `/artifacts/:id` | 검토 패널 내 미리보기 | **산출물 뷰어** — 전체 화면 | — |
| `/w/*` 워크스페이스 | 3-Pane | **읽기 전용 축약 뷰** — 주 동선 아님 | — |
| `/history` | 이력 | 접근 가능, 주 동선 아님 | — |

> **신규 화면은 SCR-M-A2HS(홈 화면 추가 안내) 1개뿐이다.** 나머지는 기존 화면의 모바일 뷰다. v1이 8개 신규 화면을 요구했던 것과 대비된다.

### 4-3. 모바일 전용 UI 규칙

| 항목 | 규칙 | 근거 |
|------|------|------|
| 최소 터치 타깃 | **44×44px** | 데스크톱 32px(DES-012 §5-2)보다 크다 |
| 표 행 높이 | **56px** | 데스크톱 36px compact는 손가락에 너무 좁다 |
| 본문 타이포 | 16px | iOS Safari는 16px 미만 입력 필드에서 자동 확대한다 |
| 가로 스크롤 | **금지** | 표는 카드 리스트로 전환 |
| 하단 안전영역 | `env(safe-area-inset-bottom)` | 홈 인디케이터 겹침 방지 |
| 액션 버튼 | 화면 하단 고정 (sticky) | 한 손 조작 |

## 5. 알림 설계

### 5-1. 알림 유형 (v1과 동일)

| 코드 | 트리거 | 우선순위 | 잠금화면 | 소리 |
|------|--------|---------|---------|------|
| **NTF-01** | APV-GATE 승인 요청 | 최고 | ✅ 전문 | ✅ |
| **NTF-02** | 등급 '높음' 승인 요청 | 높음 | ✅ 전문 | ✅ |
| **NTF-03** | 등급 '보통' 승인 요청 | 보통 | ✅ 제목만 | ✅ |
| **NTF-04** | 타임아웃 5분 전 (보통) | 보통 | ✅ | ✅ |
| **NTF-05** | Agent `failed` | 높음 | ✅ | ✅ |
| **NTF-06** | 단계 완료 / Phase 완료 | 낮음 | ❌ | ❌ (무음) |
| **NTF-07** | WIP 위반 발생 | 보통 | ✅ 제목만 | ❌ |

> 등급 '낮음' 의사결정은 알림을 보내지 않는다 (DES-013 §3-4 원칙).
> **v1 대비 제약**: 웹 푸시는 iOS에서 "방해 금지 무시" 같은 우선순위 제어가 불가능하다. NTF-01/02도 시스템 방해금지 설정을 따른다. 이 한계는 §8 D-26의 근거다.

### 5-2. 푸시 본문 규칙 (프라이버시)

```
❌ 나쁜 예 — 안건 내용이 Apple/Google 서버를 거침
   "프로덕션 배포 승인: api-server를 프로덕션에 배포합니다.
    통합 테스트 24건 전건 통과"

✅ 좋은 예 — 식별자와 최소 문구만
   title: "ClaudeManager · 승인 요청"
   body:  "등급 높음 · deploy 단계 · 1건"
   data:  { approvalId: "ap4b2c1d", url: "/approvals/ap4b2c1d" }
```

Service Worker가 `notificationclick`에서 `data.url`로 딥링크한다. 안건 제목·근거·산출물은 브라우저가 서버에서 직접 가져오므로 외부를 거치지 않는다.

### 5-3. iOS 제약 ⚠ 반드시 대응할 것

| 제약 | 내용 | 대응 |
|------|------|------|
| **홈 화면 추가 필수** | Safari 탭에서는 웹 푸시가 **동작하지 않는다.** 홈 화면에 추가한 PWA에서만 가능 | **SCR-M-A2HS 안내 화면 필수** (§6-1) |
| **iOS 16.4+** | 그 이하 버전은 웹 푸시 자체가 없음 | 버전 감지 → 안내 문구 + 이메일 대체 안내 |
| 권한 요청 시점 | 사용자 제스처 이후에만 요청 가능 | 페어링 완료 화면의 명시적 **[알림 켜기]** 버튼 |
| 백그라운드 동기화 | Background Sync 미지원 | 폴링에 의존하지 않는다. 푸시로만 갱신 |
| 저장소 정리 | 장기 미사용 시 데이터 삭제 가능 (ITP) | 토큰 만료 시 재페어링 유도, 실패해도 데이터 손실 없음 |

<!-- Android는 제약이 훨씬 적다 -->
> Android Chrome은 브라우저 탭에서도 푸시가 동작하고 제약이 적다. **문제는 iOS뿐이며, 그래서 §6-1 설치 안내가 선택이 아니라 필수다.**

### 5-4. 알림 설정 (설정 탭)

| 항목 | 기본값 | 설명 |
|------|--------|------|
| 방해 금지 시간 | 23:00 ~ 07:00 | 서버가 이 시간대 발송을 보류 (클라이언트 제어 불가하므로 **서버에서** 처리) |
| 유형별 on/off | NTF-06만 off | 사용자가 개별 조정 |
| 요약 알림 | 매일 09:00 | 대기 중 승인 건수 1건으로 묶어 발송 |

> iOS에서 우선순위 제어가 불가능하므로, **방해 금지는 클라이언트가 아니라 서버가 발송 시점에 판단**한다. 단 NTF-01(APV-GATE)은 서버 방해금지도 무시하고 발송한다.

### 6-4. 승인 확정 흐름 (WebAuthn)

```
[승인] 탭
   ↓
확인 다이얼로그
  · 안건 요약
  · 후속 동작 (DES-011 개정, 화면 10→5, main 재개)
  [ 취소 ]  [ 확인 ]
   ↓
navigator.credentials.get()   ← WebAuthn
  → Face ID / 지문
   ↓ 인증 성공
POST /api/approvals/:id/resolve
   ↓
토스트 "승인됨 · main 재개"
목록에서 제거, 탭 배지 감소
```

| 단계 | 근거 |
|------|------|
| 체크리스트 | DES-014 §5-2 S-1 — "모르는 채 누르기" 방지 |
| 확인 다이얼로그 | 후속 동작 명시. DES-011 §4-3 파괴적 작업 가드 |
| **WebAuthn** | 폰을 잃어버려도 타인이 승인할 수 없다 |
| 반려 시 사유 | DES-014 §5-2 S-2 |

> **WebAuthn 전제 조건**: HTTPS + **도메인 고정**. 터널 URL이 매번 바뀌면 등록한 passkey가 무효가 된다 → D-19에서 **고정 도메인을 제공하는 터널**을 골라야 한다(Tailscale MagicDNS, Cloudflare Tunnel 고정 호스트명). ngrok 무료 플랜처럼 URL이 바뀌는 방식은 부적합하다.
> 적용 범위는 **등급 '높음' + APV-GATE만**. '보통'까지 요구하면 마찰이 과하다. §8 D-22.

### 6-6. 페어링

QR 스캔은 브라우저에서 카메라 권한이 필요해 마찰이 크다. 모바일 웹에서는 **더 간단한 경로**가 있다.

| 방법 | 동작 | 권장 |
|------|------|------|
| **링크 페어링** | PC에서 `cm pair`가 QR + **단축 URL**을 출력 → 폰에서 URL 열면 즉시 로그인 | ✅ 1순위 |
| QR 스캔 | 폰 기본 카메라 앱으로 QR 스캔 → 브라우저가 열림 | ✅ 동일 결과 |
| 수동 입력 | 서버 URL + 시크릿 직접 입력 | 폴백 |

```
$ cm pair

  ┌ 모바일 페어링 ──────────────────────────┐
  │                                        │
  │   ██▀▀▀▀▀██  ▄▄  ██▀▀▀▀▀██             │
  │   ██ ███ ██ ▀▄▀▄  ██ ███ ██             │
  │   ██▄▄▄▄▄██  ▀ ▄  ██▄▄▄▄▄██             │
  │        (QR)                            │
  │                                        │
  │  또는 폰 브라우저에서 열기:              │
  │  https://cm.example.ts.net/p/8fk2n9     │
  │                                        │
  │  유효기간: 5분                          │

```

페어링 완료 후: JWT 저장 → **[알림 켜기]** 버튼 노출 → 푸시 구독 등록 → (iOS 미설치 시) SCR-M-A2HS 표시.

### 7-1. 신규 테이블 3종

### 7-2. 신규 엔드포인트 6종

| 메서드 | 경로 | 기능 |
|--------|------|------|

| POST | `/api/push/subscribe` | Web Push 구독 등록 |
| DELETE | `/api/push/subscribe/:id` | 구독 해제 (기기 분실 시) |

| PATCH | `/api/notification-settings` | 알림 설정 변경 |

| 승인의 파괴성에 맞는 안전장치가 있는가 | ✅ §6-4 (체크리스트 → 확인 → WebAuthn) |
| WebAuthn의 전제 조건(고정 도메인)이 명시되었는가 | ✅ §6-4, D-19 |
| 오프라인 동작 경계가 정의되었는가 | ✅ §6-7 |
| 기기 분실 대응이 있는가 | ✅ §7-2 `DELETE /api/push/subscribe/:id` |
| 모바일 전용 API가 최소화되었는가 | ✅ 6개 (§7-2) |
| 파급 영향이 빠짐없이 나열되었는가 | ✅ §9 |
